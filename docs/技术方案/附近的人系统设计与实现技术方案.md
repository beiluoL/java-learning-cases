## 1. 附近的人系统概述

### 1.1 什么是附近的人系统

「附近的人」是 **LBS（基于位置的服务）** 中最经典的一类需求：给定一个用户的实时经纬度，快速找出**以该点为中心、指定半径范围内的其他用户 / 商家 / 内容**，并按距离排序返回。

它的本质是一个 **"球面空间中的 K 近邻（KNN）查询"** 问题：

> 给定查询点 P(lng, lat) 与半径 R，求满足 `distance(P, Q) ≤ R` 的所有点 Q，并对结果按距离升序返回 Top-N。

看似只是"算个距离 + 排个序"，但当数据量达到**千万 / 亿级、位置每秒高频更新、查询 QPS 上万**时，朴素遍历（把全表用户经纬度拉出来逐个算距离）会直接打垮数据库——这正是一切设计权衡的起点。

衍生形态非常广：

- **附近的人 / 好友**：社交 App 的经典功能（微信、陌陌、Soul）。
- **附近的商家 / 门店 / 充电桩**：到店、本地生活、出行（美团、滴滴、高德）。
- **附近的动态 / 帖子 / 主播**：内容feed 的地理维度召回。
- **地理围栏（Geo-fencing）**：当用户进入某区域时触发推送（打卡、到店提醒、电子围栏告警）。

### 1.2 典型场景与规模

| 场景 | 数据量级 | 位置更新频率 | 查询特点 | 延迟要求 |
|------|---------|------------|---------|---------|
| 附近的人（社交） | 用户数亿，活跃千万 | 中（打开页/切后台时上报） | 半径 1~5km，返回 Top50 | < 200ms |
| 网约车司机/乘客匹配 | 司机百万级在线 | 高（10~30s 一次） | 半径 3km 实时召回 | < 500ms |
| 外卖/到店商家 | 商家千万 | 低（营业状态变更） | 半径 5km，含品类过滤 | < 300ms |
| 共享单车/充电桩 | 车辆/桩亿级 | 中（开锁/还车上报） | 半径 1km，就近分配 | < 500ms |
| 物流/骑手轨迹 | 轨迹点海量 | 高（秒级上报） | 区域聚合 | 容忍秒级 |

> 关键洞察：**"附近的人"系统 80% 的复杂度不在算法，而在"高频写 + 低延迟读 + 海量数据 + 敏感隐私"四股力量的拉扯**。下文第二节专门拆解。

## 2. 设计附近的人系统面临的最大难点

### 2.1 ★ 最大难点：海量地理位置数据的低延迟近邻检索

**难点本质**：地球是一个球面，但计算机索引（B+ 树、LSM 树）擅长的是 **一维有序数据** 的快速查找。经纬度是 **二维（甚至要考虑高程是三维）** 的，且是球面坐标。我们无法简单地"按经度建索引 + 按纬度建索引"就解决问题——因为要找的是"圆/方形区域内的点"，这是典型的 **多维范围查询（range query）**，二维 B+ 树无能为力。

朴素的"全表扫描 + 逐个算距离"为什么不行？

- 假设 1 亿用户，每次"附近的人"查询要算 1 亿次 `haversine`（球面距离），即便每次仅需 1μs，也要 **100 秒**——完全不可接受。
- 即便加 `WHERE lat BETWEEN ... AND ... AND lng BETWEEN ... AND ...` 的矩形框再用 B+ 树过滤，在经度跨 ±180°、高纬地区经线收缩等情况下，矩形框会严重失真、召回不准，且 B+ 树只能高效利用其中一个维度，另一个维度仍是范围扫描。

**这就是核心矛盾**：需要把"二维球面邻近关系"编码成"一维可索引结构"，且编码后仍需保持**空间邻近 ⇒ 编码值邻近**的性质，这样才能用最擅长的一维有序索引（如 ZSET / BKD / R-Tree）做快速范围/前缀检索。

业界所有方案（GeoHash、Redis Geo、ES geo_point、PostGIS、Google S2、Uber H3）都是对"如何把球面二维映射成一维并逼近真实邻近"这一问题的不同回答。

### 2.2 经纬度精度与存储 / 索引成本的平衡

- 经纬度用 `double` 存（各 8 字节，共 16 字节），精度足够；但**原始 double 无法高效做邻近检索**。
- 若编码成 GeoHash 字符串（如 8 位 ≈ 19m 精度），每多 1 位精度，索引区分度翻倍、存储与计算量上升。
- 精度太高 → 网格太碎 → 检索时要扫描更多网格、写入更分散；精度太低 → 召回误差大、需要回查精算的范围更广。
- 必须按业务半径（1km 还是 50km）反推合适的编码精度，而非盲目追求高精度。详见 [6.1](#61-geohash-精度与网格层级)。

### 2.3 实时位置更新与高频索引写入

"附近的人"的位置是**流动的**：用户一直在走，GPS 持续上报。

- 社交场景：打开页面/切前后台时上报，写峰值可控。
- 出行/物流场景：**每秒数十万~百万次位置写入**，且每次写入都要同步更新地理索引。
- 索引（无论 GeoHash 前缀、Redis ZSET、还是 R-Tree）的**高频更新**会带来：写放大、索引碎片、热点分片（同一商圈几万人更新同一网格）、一致性挑战。
- 若"写"和"读"抢同一存储，位置更新的抖动会直接拖慢"附近查询"的 P99 延迟。

### 2.4 球面距离精度（大圆距离 vs 平面近似）

- 两个点真实距离是 **大圆距离（Great-circle distance）**，用 Haversine 公式（基于球面）计算。
- 在**小范围内**（几公里），可近似用 **平面欧几里得距离**（把经纬度当直角坐标，按纬度换算米），误差 < 0.1%，性能更好。
- 但**跨纬度/跨半球**时平面近似误差急剧放大，不能用于全球范围召回。
- 工程实践：**先用编码/网格做粗筛（近似），召回候选集后再用 Haversine 精算排序**——这是性能与精度的标准折中。

### 2.5 海量数据下的检索性能与水平扩展

- 单实例 Redis / 单库 MySQL 容量与连接数有上限，亿级位置点必须**分片**。
- 但"按地理分片"会遇到**热点分布不均**：一线城市核心商圈一平方公里内可能聚集几十万人，而郊区稀疏——哈希分片会热点集中，按地理网格分片又难均衡。
- 跨区域多活时，用户 A 在深圳查"附近的人"，数据可能分布在华南分片；如何做到就近查询、低延迟，是多活架构难点。

### 2.6 隐私与安全：位置是最敏感的 PII

位置信息属于 **《个人信息保护法》定义的敏感个人信息**（可定位到具体自然人、暴露行踪习惯）。难点不仅是技术，更是合规：

- 不能无授权持续采集；不能把精确坐标明文长期存储。
- 需支持"模糊化 / 降精度 / TTL 过期 / 用户自主开关可见性"。
- 对外接口要做防爬（避免被批量拖走全城用户位置）、防定位追踪。

> 这一点在 [第 8 节](#8-安全与合规) 单独展开。它往往是项目里最容易"翻车"的隐性难点——技术能做，但做错了会吃监管罚单。

## 3. 整体设计思路与实现路径

### 3.1 设计原则

1. **读写分离、冷热分离**：位置上报（写）走高频写入通道；附近查询（读）走低延迟检索通道，二者存储可以不同。
2. **粗筛 + 精算两段式**：先用空间编码/索引做廉价粗筛（召回候选），再用距离公式精算排序（只算候选集）。永远不要让"算距离"发生在全量数据上。
3. **精度随场景自适应**：编码精度、检索半径、返回条数都可配置，不追求统一高精度。
4. **TTL 与惰性清理**：离线用户的位置自动过期（Redis 天然支持），避免脏数据污染结果。
5. **隐私默认最小化**：默认降精度、默认授权才可见、默认短期存储。

### 3.2 分层架构

```
┌──────────────────────────────────────────────────────────────┐
│                        客户端 (App / Web)                       │
│   定位(GPS/基站/WiFi) → 上报位置 → 拉取"附近列表"              │
└───────────────┬───────────────────────────┬────────────────────┘
                │ 上报(写)                    │ 查询(读)
                ▼                            ▼
┌──────────────────────┐        ┌──────────────────────────────┐
│  位置上报服务          │        │  附近查询服务 (API)            │
│  (无状态, Spring Boot) │        │  (无状态, Spring Boot)        │
│  - 校验/限流           │        │  - 参数校验/半径控制           │
│  - 写入 Geo 索引        │        │  - 调用 Geo 检索              │
│  - TTL 管理            │        │  - 精算+排序+过滤             │
└──────────┬───────────┘        └──────────────┬───────────────┘
           │                                   │
           ▼                                   ▼
┌──────────────────────┐        ┌──────────────────────────────┐
│  实时位置存储 (热)      │        │  地理检索索引 (近邻检索)        │
│  Redis / 内存表        │        │  Redis Geo / ES / PostGIS     │
│  (高频写, TTL)         │        │  (粗筛)                       │
└──────────┬───────────┘        └──────────────┬───────────────┘
           │ 异步落库                          ▲ 精算回源
           ▼                                   │
┌──────────────────────┐        ┌──────────────────────────────┐
│  持久化存储 (冷/全量)   │        │  业务元数据 (用户画像/状态)     │
│  MySQL / PostGIS       │        │  MySQL / 缓存                  │
│  (位置历史/审计)        │        │  (性别/头像/在线状态 过滤)      │
└──────────────────────┘        └──────────────────────────────┘
```

**分工说明**：

- **实时位置存储（热）**：只保留"当前在线/近期活跃"的位置，高频写、带 TTL。可用 Redis（含 Redis Geo）承载。
- **地理检索索引**：专门服务"附近"查询，做粗筛。可以是 Redis Geo、Elasticsearch geo_point、或 PostGIS。
- **持久化存储（冷）**：全量用户的最新位置 + 历史轨迹，供审计、离线分析、补录。MySQL + 空间索引或 PostGIS。
- **业务元数据**：头像、昵称、性别、在线状态等，用于结果过滤与展示，与位置数据解耦。

### 3.3 核心概念模型

| 概念 | 字段 | 说明 |
|------|------|------|
| 位置点（LocationPoint） | `userId, lng, lat, accuracy, updateTime, ttl` | 用户的实时位置快照 |
| GeoHash 编码 | `geohash(6~8位)` | 由经纬度算出的网格编码，用于粗筛 |
| 查询请求（NearbyQuery） | `lng, lat, radius(m), limit, filters` | 中心点 + 半径 + 过滤条件 |
| 查询结果（NearbyResult） | `userId, distance(m), ...业务字段` | 去重、精算、排序后的结果 |

### 3.4 核心流程：位置上报与附近查询

**流程 A — 位置上报（写路径）**

```
1. 客户端采集 GPS → {userId, lng, lat, accuracy}
2. 网关鉴权 + 限流
3. 位置上报服务：
   a. 校验坐标合法性（lat∈[-90,90], lng∈[-180,180]，且在中国境内需额外合规校验）
   b. 计算 geohash（如 7 位，约 76m 精度）
   c. 写入 Redis Geo（GEOADD，带 TTL 或独立 ZSET 维护活跃）
   d. 异步投递 MQ → 同步落 MySQL/PostGIS（最终一致）
4. 返回 ack（或静默）
```

**流程 B — 附近查询（读路径，两段式）**

```
1. 客户端请求：{lng, lat, radius=3000m, limit=50, 过滤: 性别=女, 在线=是}
2. 附近查询服务：
   a. 计算中心点 geohash（精度按 radius 反推）
   b. 粗筛：用 Redis Geo GEOSEARCH / ES geo_distance / PostGIS ST_DWithin
            召回"候选集"（可能略大于真实圆，含边界外一点）
   c. 精算：对候选集逐个 Haversine 计算真实距离，过滤掉圈外点
   d. 过滤：按业务字段（性别/在线）二次过滤
   e. 排序：按 distance 升序，取 Top-N
   f. 补全业务字段（昵称/头像/距离文案"1.2km"）
3. 返回结果列表
```

> 关键：**b 粗筛可召回"偏多但绝不漏"的候选集，c 精算保证"圈内准确、圈外剔除"**。这样把昂贵的精确距离计算限制在候选集规模（通常几百~几千），而非全量。

### 3.5 关键技术选型决策

选型由三个旋钮决定，按下表对号入座：

| 你的现状 | 推荐方案 |
|---------|---------|
| 数据量小（< 百万）、要快上线、已有 Redis | **Redis Geo**（首选，零额外组件） |
| 需要"地理 + 全文 + 过滤 + 聚合"联合检索 | **Elasticsearch**（geo_point + bool query） |
| 位置是系统核心、需要复杂空间运算/历史轨迹 | **PostGIS**（空间数据库天花板） |
| 已有 MySQL、查询简单、量级中等 | **MySQL 空间索引**（ST_Distance_Sphere + SPATIAL INDEX） |
| 超大规模、自研、要极致可控 | **GeoHash 自研 + 分片存储（Redis/MongoDB）** |
| 出行/物流海量轨迹 + 实时围栏 | **GeoHash 分片 + 流式计算（Flink）** |

### 3.6 实现路径（演进路线）

- **阶段 0（Demo / 小流量）**：MySQL 两列 `lng/lat` + 矩形框 `BETWEEN` 粗筛 + 内存 Haversine 精算。能跑通，量级 < 10 万。

- **阶段 1（生产可用，推荐起点）**：引入 **Redis Geo**。位置写 Redis，查询走 `GEOSEARCH`。代码改动极小，性能提升 1~2 个数量级。绝大多数"附近的人"业务到此已够用。

- **阶段 2（检索复杂化）**：需要"附近 + 关键词 + 属性过滤 + 聚合热力图" → 引入 **Elasticsearch**，geo_point 与业务字段同索引。

- **阶段 3（空间为核心能力）**：轨迹、围栏、复杂拓扑 → **PostGIS**；或超大规模自研 **GeoHash 分片集群**。

## 4. 可行的技术方案与业界成熟方案

### 4.1 地理空间索引基础原理

理解下面几种"降维"思路，是看懂所有方案的钥匙。

**(1) GeoHash — 把二维"交错"成一维字符串**

将纬度、经度区间不断二分，交替取二进制位（经度一位、纬度一位…），拼接成 bit 串后每 5 位 base32 编码成一个字符。结果：**地理越邻近，GeoHash 公共前缀越长**。

- 优点：实现简单、可前缀检索（同一前缀 = 同一网格）、天然支持分片。
- 缺点：**边界效应**——两点仅一街之隔，却可能因落在不同网格而前缀不同（见 [6.2](#62-边界漏查问题与周边-8-格召回)）。需用"周边 8 格"补偿。
- 代表：Redis Geo 内部、MongoDB 2d、自研方案均基于其变体。

**(2) Google S2 — 球面四叉树 Cell ID**

把球面投影到立方体再细分，用 64 位整数 Cell ID 表示网格，层级 0~30。覆盖均匀、无 GeoHash 的纵横比扭曲，适合全球均匀分布。Uber、Google 内部大量使用。

**(3) Uber H3 — 六边形网格**

用六边形（而非正方形）把地球划分成层级网格。六边形邻居数固定（6 个）、无方向偏差，特别适合"蜂窝聚合 / 密度图 / 区域统计"。Uber 开源。

**(4) R-Tree — 多维空间索引**

用"最小外接矩形（MBR）"嵌套组织空间对象，是 PostGIS、MySQL 空间索引的底层结构。擅长"范围查询/相交查询"，但不擅长"最近邻 KNN"（需特殊算法）。

**(5) BKD Tree（Lucene）**

Elasticsearch 5.x 起 geo_point 用 BKD 树（k-d tree 的块化变体）索引，兼顾写入与 KNN 范围查询，性能优于老的 geohash grid 方案。

### 4.2 成熟开源方案对比

| 方案 | 底层 | 邻近查询 | 精度 | 写入吞吐 | 适合场景 | 主要短板 |
|------|------|---------|------|---------|---------|---------|
| **Redis Geo** | ZSET + 52位 GeoHash 整数 | `GEOSEARCH` 半径/矩形 | ~厘米（52bit） | 高（内存） | 中小规模实时附近 | 数据全内存、容量受限、无复杂过滤 |
| **Elasticsearch** | BKD Tree（geo_point） | `geo_distance` / `geo_bounding_box` | 高 | 中（近实时） | 地理+全文+聚合联合检索 | 重、运维成本、近实时非强一致 |
| **PostGIS** | R-Tree(GiST) + 球面运算 | `ST_DWithin` / `<->` KNN | 最高（球面） | 中 | 空间为核心、轨迹/围栏 | 需 Postgres、扩展性靠分库 |
| **MongoDB** | 2dsphere(球面)/2d(平面) | `$near` / `$geoWithin` | 高 | 中高 | 文档型+地理一体 | 地理运算不及 PostGIS 丰富 |
| **MySQL 空间** | R-Tree(InnoDB) | `ST_Distance_Sphere`/`ST_DWithin` | 高 | 中 | 已有 MySQL、简单查询 | 大数据量 KNN 性能一般 |
| **GeoMesa** | Accumulo/HBase | 时空索引 | 高 | 很高 | 海量时空数据(政府/物联网) | 重、学习曲线陡 |

**Redis Geo 内部细节（面试常考）**：`GEOADD` 实际是把 member 的 52 位整数 GeoHash 作为 score 写入一个 ZSET。半径查询时，先算出中心点所在 GeoHash 网格及周围 8 个邻居网格（按搜索半径确定精度），对在网格范围内的 score 范围做 `ZRANGEBYSCORE`，再对候选逐个用 Haversine 精确过滤。因此 Redis Geo 本质是"GeoHash + ZSET"的工程封装，单 key 不宜过大（建议按城市/网格拆分）。

### 4.4 自研 vs 采购决策

- **默认不要自研**空间索引内核。GeoHash/ZSET/PostGIS 已经把最难的"球面→一维"问题解决了。
- **自研只在**：超大规模（亿级在线）、既有中间件不合适、或需要特殊网格语义（如 H3 蜂窝）时。此时通常也只是"用 GeoHash/S2 做分片路由 + 复用 Redis/Mongo 做存储"，而非重写索引算法。
- **采购/云**适合：要快速上线、不想运维 ES 集群、或坐标合规（GCJ-02）想交给地图厂商兜底。

## 5. Java 技术栈的具体实现

以下给出可落地的 Java 代码片段（基于 Spring Boot 3.x + Java 17）。**优先推荐 Redis Geo 路线**，再补充 ES / MySQL 路线供横向对比。

### 5.1 GeoHash 原理与 Java 自研实现

先手写一个 GeoHash 编解码，理解底层后，用 Redis Geo/ES 时你才知道它们在做什么。

```java
/**
 * 最小可用 GeoHash 编码（经度优先交替编码，base32）。
 * 仅用于教学理解；生产请用 Redis Geo / ES，不要自己造索引。
 */
public final class GeoHashUtil {
    private static final String BASE32 = "0123456789bcdefghjkmnpqrstuvwxyz";
    private static final int[] BITS = {16, 8, 4, 2, 1};
    // 各精度下的网格经纬度跨度（度），用于"周边格"计算
    private static final double[] LAT_DELTA = {90, 45, 11.25, 5.625, 1.40625, 0.703125, 0.17578125, 0.087890625};
    private static final double[] LNG_DELTA = {180, 90, 22.5, 11.25, 2.8125, 1.40625, 0.3515625, 0.17578125};

    /** 编码：even=true 时处理经度位 */
    public static String encode(double lat, double lng, int precision) {
        double[] latRange = {-90, 90};
        double[] lngRange = {-180, 180};
        StringBuilder sb = new StringBuilder();
        boolean even = true;
        int bit = 0, ch = 0;
        while (sb.length() < precision) {
            if (even) {
                double mid = (lngRange[0] + lngRange[1]) / 2;
                if (lng >= mid) { ch |= BITS[bit]; lngRange[0] = mid; }
                else { lngRange[1] = mid; }
            } else {
                double mid = (latRange[0] + latRange[1]) / 2;
                if (lat >= mid) { ch |= BITS[bit]; latRange[0] = mid; }
                else { latRange[1] = mid; }
            }
            even = !even;
            if (bit < 4) bit++;
            else { sb.append(BASE32.charAt(ch)); bit = 0; ch = 0; }
        }
        return sb.toString();
    }

    /** 返回中心点 + 周围 8 格共 9 个 GeoHash（解决边界漏查，见 6.2） */
    public static List<String> neighbors(double lat, double lng, int precision) {
        double latStep = LAT_DELTA[precision - 1];
        double lngStep = LNG_DELTA[precision - 1];
        List<String> res = new ArrayList<>();
        for (int dLat = -1; dLat <= 1; dLat++) {
            for (int dLng = -1; dLng <= 1; dLng++) {
                res.add(encode(lat + dLat * latStep, lng + dLng * lngStep, precision));
            }
        }
        return res;
    }

    /** Haversine 球面距离（米） */
    public static double haversine(double lat1, double lng1, double lat2, double lng2) {
        final int R = 6371000; // 地球半径(米)
        double dLat = Math.toRadians(lat2 - lat1);
        double dLng = Math.toRadians(lng2 - lng1);
        double a = Math.sin(dLat / 2) * Math.sin(dLat / 2)
                 + Math.cos(Math.toRadians(lat1)) * Math.cos(Math.toRadians(lat2))
                 * Math.sin(dLng / 2) * Math.sin(dLng / 2);
        return R * 2 * Math.atan2(Math.sqrt(a), Math.sqrt(1 - a));
    }
}
```

> 踩坑提示：自研 GeoHash 只建议用于**理解原理、做分片路由、或做缓存 key**。真正要"按半径检索 + 排序"，请用成熟方案，别用 `LIKE 'wx4g%'` 扫字符串——那在亿级数据上依然是灾难。

### 5.2 Redis Geo 实战（Spring Data Redis）

引入依赖：`spring-boot-starter-data-redis`（底层 Lettuce）。

```java
@Service
public class NearbyService {
    private final StringRedisTemplate redis;
    // 位置键：按城市分片，避免单 ZSET 过大
    private static final String KEY = "geo:user:location:%s"; // %s = cityCode

    public NearbyService(StringRedisTemplate redis) { this.redis = redis; }

    /** 上报/更新位置 */
    public void upsertLocation(Long userId, double lng, double lat, String cityCode) {
        String key = KEY.formatted(cityCode);
        // point 顺序是 (经度, 纬度)！与直觉相反，易错
        redis.opsForGeo().add(key, new Point(lng, lat), String.valueOf(userId));
        // 如需 TTL：Redis Geo 没有原生 TTL，可额外维护活跃 ZSET 或定时清理离线用户
    }

    /** 查询附近的人（半径内，按距离升序） */
    public List<NearbyUser> nearby(double lng, double lat, double radiusMeters,
                                    long limit, String cityCode) {
        String key = KEY.formatted(cityCode);
        Distance dist = new Distance(radiusMeters, Metrics.METERS);
        Circle circle = new Circle(new Point(lng, lat), dist);
        // 返回距离（米）并按距离排序
        GeoResults<GeoLocation<String>> results =
            redis.opsForGeo().search(key, circle,
                GeoSearchCommandArgs.newGeoSearchArgs().limit(limit).includeDistance());

        List<NearbyUser> list = new ArrayList<>();
        for (GeoResult<GeoLocation<String>> r : results) {
            Long uid = Long.valueOf(r.getContent().getName());
            double meters = r.getDistance().getValue();
            list.add(new NearbyUser(uid, meters));
        }
        return list;
    }
}
```

**要点**：

- `Point(lng, lat)` —— **经度在前、纬度在后**，与 GeoHash 的"纬度在前"恰好相反，极易写反。
- Redis Geo 单 key 本质是 ZSET，**不建议把全国用户塞一个 key**（内存 + 单 key 过大）。按 `cityCode` 或 GeoHash 前缀分片是标配。
- GeoHash 本身无 TTL；离线用户位置需业务侧定时清理（如维护 `lastActive` ZSET，过期 `ZREMRANGEBYSCORE` 删掉）。

### 5.3 Elasticsearch 地理检索实战

适合"附近 + 关键词 + 属性过滤"联合检索。索引映射：

```json

  "mappings": {
    "properties": {
      "userId":   { "type": "long" },

    }
  }
}
```

查询（geo_distance + bool 过滤）：

```json
{
  "query": {
    "bool": {
      "must":   { "match": { "nickname": "咖啡" } },
      "filter": [
        { "geo_distance": { "distance": "3km", "location": { "lat": 22.54, "lon": 114.06 } } },
        { "term": { "gender": "female" } },
        { "term": { "online": true } }
      ]
    }
  },
```

### 5.4 持久化存储：MySQL 空间索引 / PostGIS

**MySQL 8（InnoDB 空间索引，R-Tree）**：

```sql
CREATE TABLE user_location (
  user_id   BIGINT PRIMARY KEY,
  geo_point POINT NOT NULL,
  update_time DATETIME,
  SPATIAL INDEX idx_geo (geo_point)
) ENGINE=InnoDB;

-- 写入（注意函数里是 POINT(经度, 纬度)）
INSERT INTO user_location(user_id, geo_point, update_time)
VALUES (1001, ST_PointFromText('POINT(114.06 22.54)'), NOW())
ON DUPLICATE KEY UPDATE geo_point = ST_PointFromText('POINT(114.06 22.54)'), update_time = NOW();

-- 查询 3km 内、按距离排序（ST_Distance_Sphere 返回米）
SELECT user_id,
       ST_Distance_Sphere(geo_point, ST_PointFromText('POINT(114.06 22.54)')) AS dist_m
FROM user_location
WHERE ST_DWithin(geo_point, ST_PointFromText('POINT(114.06 22.54)'), 3000)
ORDER BY dist_m ASC
LIMIT 50;
```

> 注意：`ST_DWithin` 第三个参数是**米**（MySQL 8 的 `ST_DWithin(geom1, geom2, distance)` 对地理几何按米计）。`ST_Distance_Sphere` 同样返回米。

**PostGIS（PostgreSQL，空间能力天花板）**：

```sql
CREATE EXTENSION postgis;
CREATE TABLE user_location (
  user_id BIGINT PRIMARY KEY,
  geom    GEOMETRY(Point, 4326),   -- 4326 = WGS-84
  update_time TIMESTAMP
);
CREATE INDEX idx_geom ON user_location USING GIST (geom);

-- 球体精确距离 + 索引友好的 KNN（<-> 是距离操作符，可用 GiST 索引加速）
SELECT user_id,
       ST_DistanceSphere(geom, ST_SetSRID(ST_MakePoint(114.06, 22.54), 4326)) AS dist_m
FROM user_location
WHERE ST_DWithin(geom, ST_SetSRID(ST_MakePoint(114.06, 22.54), 4326), 3000)
ORDER BY geom <-> ST_SetSRID(ST_MakePoint(114.06, 22.54), 4326)
LIMIT 50;
```

`geom <-> point` 是 PostGIS 的 **KNN 距离算子**，配合 GiST 索引可做真正的"最近邻"排序，性能远好于先算距离再排序。

### 5.5 位置上报与实时更新链路

```java
@RestController
@RequestMapping("/location")
public class LocationController {
    private final NearbyService nearby;
    private final KafkaTemplate<String, String> kafka;

    /** 上报位置：写热存储(Redis Geo) + 异步落冷存储(MySQL) */
    @PostMapping("/report")
    public void report(@RequestBody @Valid LocationReq req) {
        // 1) 校验坐标合法 + 国内合规范围
        if (!valid(req.lat(), req.lng())) throw new IllegalArgumentException("invalid coord");
        // 2) 实时位置写入 Redis Geo（热，供查询）

            JSON.toJSONString(new LocEvent(req.userId(), req.lng(), req.lat(), System.currentTimeMillis())));
    }
}

// 消费端：批量写 MySQL/PostGIS，失败重试进死信
@KafkaListener(topics = "loc-topic")
public void consume(List<LocEvent> batch) { locationRepo.batchUpsert(batch); }
```

**设计要点**：

- 热路径（Redis）保低延迟查询；冷路径（MQ → MySQL）异步、可削峰、可重试。
- 离线用户：维护 `lastActive` 时间戳，定时任务清理 Redis 中过期位置，避免"附近的人"里出现早已离开的人。
- 高频写入用**批量**（Kafka 攒批 / Redis Pipeline）降低开销。

### 5.6 分片与空间数据扩展

当单 Redis / 单库撑不住：

- **按 GeoHash 前缀分片**：取经纬度 4~5 位 GeoHash 作为分片键，同一区域的人落在同一分片，查询时只需查"中心格 + 周边格"对应的几个分片。
- **按城市分片**：简单直接（如 5.2 的 `cityCode`），但跨城查询需聚合。
- **一致性哈希**：Redis 集群天然按 key 哈希分片；若自定义分片，用一致性哈希减少扩缩容时的数据迁移。
- **读写分离**：MySQL 主写从读，查询走从库；Redis 多副本分担读。

## 6. 核心难点落地：近邻检索精度与性能平衡

### 6.1 GeoHash 精度与网格层级

GeoHash 每多 1 位字符，网格在经度和纬度上各细分约一倍，精度约提升为原来的 1/4（面积）。

| 字符数 | 网格宽(经度) | 网格高(纬度) | 网格面积误差(约) | 适用半径 |
|-------|------------|------------|---------------|---------|
| 4 | ~20 km | ~20 km | ~±20 km | > 50 km |
| 5 | ~5 km | ~5 km | ~±2.4 km | 10~50 km |
| 6 | ~1.2 km | ~0.6 km | ~±0.6 km | 1~10 km |
| 7 | ~0.15 km | ~0.15 km | ~±0.076 km | < 1 km |
| 8 | ~0.04 km | ~0.02 km | ~±0.019 km | 室内/楼宇级 |

**工程经验**：选比"查询半径"更小的网格精度。例如查 3km 半径，用 6 位（~0.6km 网格）即可，粗筛框覆盖大约 `(3/0.6*2+1)^2 ≈ 121` 个网格，召回可控；若用 8 位则网格过多、检索分片数爆炸。

### 6.2 边界漏查问题与周边 8 格召回

GeoHash 最大陷阱：**两点真实距离很近，却落在不同网格，导致前缀不同，前缀检索漏掉**。

例如查询中心在网格 G，真实圆（半径 R）可能延伸到相邻网格 G1~G8。若只搜 G 自己，圆周附近的候选会被漏。

**标准解法（Redis Geo / 自研都用）**：

1. 根据半径 R 确定网格精度 p（如 6 位）。
2. 计算中心点的 9 个网格：中心 G + 上/下/左/右/四角共 **8 个相邻格**（见 5.1 `neighbors()`）。
3. 对这 9 个网格分别做前缀检索 / 范围检索，合并候选。
4. 再用 Haversine 精算，剔除圆外点。

```
        ┌───┬───┬───┐
        │G8 │G1 │G2 │   中心 G 与周围 8 格
        ├───┼───┼───┤   搜索圈若跨格，必落在这 9 格内
        │G7 │ G │G3 │
        ├───┼───┼───┤
        │G6 │G5 │G4 │
        └───┴───┴───┘
```

> 极端情况（查询半径远大于网格）：需扩到 5×5、7×7 格。Redis 内部按半径自动选精度与扩格，开发者无需手动处理——这也是推荐 Redis Geo 而非裸 GeoHash 的理由。

### 6.3 距离排序与精算（Haversine）

粗筛召回的候选，必须用 **Haversine 大圆公式**算真实距离再排序（见 5.1）。小范围内也可用平面近似提速：

```java
// 小范围(几km)平面近似：1°纬度≈111320m，1°经度≈111320*cos(lat) m
double dx = (lng2 - lng1) * 111320 * Math.cos(Math.toRadians(lat1));
double dy = (lat2 - lat1) * 111320;
double flatDist = Math.sqrt(dx * dx + dy * dy); // 米，误差<0.1%
```

工程上：**粗筛用编码，排序用 Haversine，超大规模小范围可用平面近似**，三层递进。

### 6.4 精度 vs 性能权衡速查表

| 诉求 | 选什么 | 代价 |
|------|--------|------|
| 最快上线、量级中 | Redis Geo | 内存成本、单 key 上限 |
| 最高空间精度 | PostGIS（球面） | 运维 Postgres、扩展性靠分库 |
| 最省存储、可前缀分片 | GeoHash 字符串 | 需自己处理边界与精算 |
| 全球均匀、无扭曲 | Google S2 | 学习曲线、需自研存储 |
| 蜂窝聚合/密度 | Uber H3 | 非主流、工具链少 |
| 地理+搜索一体 | Elasticsearch | 重、近实时 |

## 7. 性能、扩展性与高可用

### 7.1 多级缓存挡热点

- **进程内缓存（Caffeine）**：同一商圈的高频查询结果短时间缓存（如 3s），应对"万人同时刷同一区域"。
- **Redis 副本**：读分摊到多个 replica。
- **结果缓存**："附近的人"结果本身可缓存，因位置变化慢、容忍秒级延迟。

### 7.2 分片与一致性哈希

- 位置数据按 GeoHash 前缀 / 城市分片，避免单点过热。
- Redis Cluster 按 key 哈希分片；扩缩容用一致性哈希，减少数据迁移。
- 查询跨片时，并发查多个分片再归并排序（类似搜索引擎的 scatter-gather）。

### 7.3 限流与降级

- 上报接口：按 userId + IP 限流（Guava RateLimiter / Sentinel），防位置刷屏。
- 查询接口：半径封顶（如最大 50km）、返回条数封顶（如 200），防"全城扫描"类滥用查询。
- 降级：Geo 索引不可用时，降级为"仅返回缓存结果"或"暂不可查附近"，保主流程。

### 7.4 多活与容灾

- Redis/ES/MySQL 均做跨可用区副本，主宕自动切换。
- 位置数据可重建（用户重新上报即恢复），容忍短暂丢失。
- 多活按地理区域分流（华北/华东/华南各一集群），就近读写，降低跨区延迟。

## 8. 安全与合规

### 8.1 位置隐私保护（最高优先级）

位置是**敏感个人信息**，设计上必须"默认隐私最小化"：

- **授权采集**：仅在用户明确同意、且功能确需时采集；提供"隐藏我的位置"开关。
- **降精度存储**：对外展示与检索可用 6~7 位 GeoHash（百米级），非精确坐标；精确坐标仅临时存在于内存。
- **TTL 过期**：离线/不活跃用户位置自动失效，不长期留存。
- **距离模糊化**：对外只显示"1.2km""<100m"，不暴露精确米数。
- **防拖库**：附近查询必须带半径上限 + 频控 + 鉴权，禁止无限制批量拉取全量坐标。

### 8.2 法律边界（《个人信息保护法》语境）

- 位置属于敏感个人信息，处理需**单独同意**、告知目的与范围。
- 不得超范围留存、不得向第三方非法提供。
- 用户有查询、更正、删除其位置数据的权利（提供"清除我的位置"能力）。
- 跨境业务注意数据出境合规。

### 8.3 工程护栏

- 所有位置写入/查询接口强制鉴权（token / 签名）。
- 坐标做合法性 + 国内范围校验，拦截异常值（如 `(0,0)` Null Island、境外异常点）。
- 接口增加防爬：行为风控（同用户高频查询不同点 = 在扫全城）、验证码/滑块。
- 审计日志：位置访问留痕，便于合规追溯。

## 9. 总结与学习路径

### 9.1 一句话总结

「附近的人」的本质是**球面上的 K 近邻查询**，最大难点是把二维球面邻近关系编码成一维可索引结构（GeoHash/S2/H3/R-Tree/BKD），并以"粗筛 + 精算"两段式在海量、高频、实时、敏感四重约束下取得平衡；**中小规模首选 Redis Geo，复杂检索上 Elasticsearch，空间为核心选 PostGIS**。

### 9.2 技术选型速查

| 你的情况 | 直接选 |
|---------|-------|
| 已有 Redis、要快 | Redis Geo |
| 地理+搜索+过滤 | Elasticsearch |
| 轨迹/围栏/精确空间 | PostGIS |
| 已有 MySQL、量小 | MySQL 空间索引 |
| 亿级在线、自研 | GeoHash 分片 + Redis/Mongo |

### 9.3 Java 工程师学习路径

1. **懂原理**：手写 GeoHash 编码（本文 5.1）+ 理解"球面→一维"。
2. **会调包**：Spring Data Redis `opsForGeo` 跑通上报+查询（阶段 1）。
3. **会检索**：Elasticsearch geo_point + bool + sort（阶段 2）。
4. **会存储**：MySQL `ST_Distance_Sphere` / PostGIS KNN（阶段 3）。
5. **懂工程**：分片、TTL、限流、缓存、隐私合规（第 7、8 节）。
6. **踩过坑**：坐标系转换（GCJ-02）、Point(经度,纬度) 顺序、边界漏查、单 key 过大。

### 9.4 常见坑位提醒

- ❌ 用 `double lng/lat` 两列 + `BETWEEN` 就敢上生产（大数据量必慢、且矩形框失真）。
- ❌ `Point(lat, lng)` 写反（多种 API 顺序是经度在前！）。
- ❌ 忽视坐标系：国内把 WGS-84 当 GCJ-02 用，偏移几百米。
- ❌ 全国用户塞一个 Redis Geo key（内存爆炸 + 单 key 上限）。
- ❌ 只查中心网格不做"周边 8 格"召回，圆周附近漏人。
- ❌ 位置无 TTL、无授权、精确坐标长期明文存，触碰合规红线。
- ❌ 不做半径/条数封顶，被恶意"全城扫描"。

### C. 关键术语

- **GeoHash**：经纬度交错编码成一维字符串，公共前缀代表邻近。
- **Haversine**：计算球面两点大圆距离的三角函数公式。
- **R-Tree / GiST**：多维空间索引结构（PostGIS/MySQL 底层）。
- **BKD Tree**：Lucene 用于 geo_point 的 k-d 树变体。
- **KNN**：K-Nearest Neighbors，最近邻查询。
- **WGS-84 / GCJ-02 / BD-09**：GPS 原始 / 国测局加密 / 百度加密坐标系。
- **Geo-fencing**：地理围栏，进入/离开区域触发事件。
