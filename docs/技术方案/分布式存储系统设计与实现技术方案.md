## 1. 分布式存储系统概述

### 1.1 什么是分布式存储系统

分布式存储系统是**将数据分散存放在多台通过网络互联的普通服务器上，对外却表现为「一个」容量近乎无限、可靠性远高于单机的统一存储服务**的系统。

它要回答的核心问题是：机器会坏、磁盘会损、网络会断、机房会停电——**如何用一堆不可靠的廉价硬件，构建出一个可靠的存储整体？**

与单机存储（本地文件系统、单实例 MySQL）相比，本质差异有四点：

| 维度 | 单机存储 | 分布式存储 |
|------|----------|------------|
| 容量上限 | 受单机磁盘限制 | 横向扩展，PB~EB 级 |
| 故障语义 | 机器挂 = 服务挂 + 数据可能丢 | 单点故障对用户透明 |
| 一致性 | 天然强一致（单副本） | 多副本，一致性需协议保障 |
| 复杂度来源 | 磁盘 I/O、锁 | **网络分区、时钟、部分失败（Partial Failure）** |

> **最关键的认知**：分布式存储的复杂度不来自"数据变多了"，而来自"**部分失败**"——一次写入，3 个副本可能 2 成功 1 超时，而"超时"既不代表成功也不代表失败。单机世界里不存在这种"薛定谔的状态"，它是所有分布式存储设计的复杂度源头。

### 1.2 五种形态：先分清你要做的是哪一种

"分布式存储"是一个大伞，下面至少有五类差异极大的系统，**设计取舍完全不同**，选型前必须先定位：

| 形态 | 抽象接口 | 语义特征 | 典型代表 | 典型场景 |
|------|----------|----------|----------|----------|
| **分布式块存储** | 读写扇区（LUN/裸设备） | 低延迟、强一致、可挂载为磁盘 | Ceph RBD、阿里云 ESSD | 云主机系统盘、数据库底层 |
| **分布式文件系统** | POSIX 目录树（open/read/seek） | 有层级、有 rename、需元数据服务 | HDFS、CephFS、JuiceFS | 大数据分析、AI 训练集 |
| **分布式对象存储** | Key → 不可变对象（PUT/GET） | 扁平、无 rename、HTTP 接口、海量小/大文件 | S3、MinIO、Ceph RGW | 图片视频、备份、数据湖 |
| **分布式 KV 存储** | get/put/scan | 毫秒级、高并发点查 | TiKV、Cassandra、Redis Cluster | 缓存、会话、元数据 |
| **分布式表格/数据库** | 行列 + 事务 + SQL | 事务、索引、二级查询 | HBase、TiDB、OceanBase、Spanner | 业务在线库、实时宽表 |

**一句话区分对象存储与文件系统**：文件系统要支持"把目录 A 重命名成 B"（一次元数据事务牵动整棵子树），对象存储不支持——正是这个"缺失的功能"让对象存储得以做到近乎无限扩展。**能力上的减法，换来了扩展性上的加法**，这是分布式系统设计中最典型的取舍思维。

### 1.3 一次写入背后发生了什么

理解分布式存储，最好的切入点是跟踪一次 `PUT /bucket/photo.jpg`（3 副本）的完整链路：

```
Client
  │ 1. 问元数据：这个对象该写到哪？
  ▼
[Metadata / Master]  一致性哈希或分片表 → 定位到 Shard-7
  │                  Shard-7 的副本：Node-A(主)、Node-B、Node-C
  ▼
[Node-A 主副本]
  │ 2. 写 WAL（先写日志，落盘 fsync）  ← 保证宕机不丢
  │ 3. 写内存结构 MemTable
  │ 4. 并行复制给 B、C（Raft/主从复制）
  │        ├──► Node-B  写 WAL + 内存 → ACK
  │        └──► Node-C  写 WAL + 内存 → ACK
  │ 5. 收到多数派(2/3)ACK → 认为"已提交"
  ▼
Client 收到成功
  │
  ▼（后台异步）
[Compaction 落盘成 SSTable] + [校验和巡检] + [副本数不足时自动补副本]
```

这条链路里埋着本文要展开的全部核心问题：

- 第 1 步 → **元数据如何管理，会不会成为瓶颈/单点**（3.4 节）
- 第 2 步 → **如何保证宕机不丢数据**（WAL + fsync，3.5 节）
- 第 4~5 步 → **一致性与可用性如何取舍**（多数派、Raft，2.1 / 3.3 节）
- 后台部分 → **静默数据损坏、自动恢复、扩容再平衡**（2.4 / 6.x 节）

## 2. 设计分布式存储系统面临的最大难点

先说结论。

> ### ★ 最大难点：在网络必然分区、节点必然故障的前提下，同时保证「数据不丢、不错、随时可用、还要快」——即 **一致性（Consistency）、可用性（Availability）、性能（Latency）三者的不可能三角**。
>
> 这不是某个算法能解决的问题，而是一个**必须由业务语义来决定取舍点**的架构命题。存储系统与其他系统的根本区别在于：**它是数据的最终归宿，没有"重试一次就好了"的退路**。上游服务算错了可以重算，存储丢了就是永久丢失。

下面把这个总难点拆解为六个具体挑战，并逐一说明"为什么难"。

### 2.1 ★ 一致性与可用性的取舍：CAP 与 PACELC

**CAP 定理**：在发生网络分区（P）时，系统只能在一致性（C）与可用性（A）之间选一个。

必须澄清两个常见误解：

1. **CAP 不是"三选二"**，而是"P 必然发生，所以本质是 CP 与 AP 之间二选一"。网络分区不是你能选择放弃的选项。
2. **CAP 是极端情况下的取舍**，日常无分区时系统可以同时满足 C 和 A。所以更实用的模型是 **PACELC**：

```
if (Partition)  →  在 A 与 C 之间选  (PA / PC)
else            →  在 Latency 与 Consistency 之间选  (EL / EC)
```

| 类型 | 含义 | 代表系统 |
|------|------|----------|
| **PC/EC** | 分区时保一致性，正常时也宁可牺牲延迟保一致 | HBase、TiKV、etcd、Spanner |
| **PA/EL** | 分区时保可用，正常时也优先低延迟（最终一致） | Cassandra、Dynamo、Riak |
| **PC/EL** | 分区时保一致，正常时优先低延迟 | MongoDB（默认配置下） |

**难点在于**：这个选择不是技术偏好，而是业务语义决定的。

- 账户余额、库存扣减 → 必须 CP，宁可拒绝服务也不能出现"钱变多了"。
- 用户头像、商品浏览量、日志 → AP 更合适，短暂看到旧数据无害，但服务不可用会掉用户。
- 而**同一个系统内不同数据可能要求不同级别**，这才是真正的工程复杂度所在。

**一致性模型也不是二元的**，而是一个谱系：

```
强一致 ────────────────────────────────► 弱一致
线性一致性     顺序一致性   因果一致性   读己之写   最终一致性
(Linearizable) (Sequential) (Causal)   (RYW)     (Eventual)
  ↑最贵                                            ↑最便宜
  etcd/Spanner   ZooKeeper   COPS     会话粘滞    Cassandra默认
```

### 2.2 数据如何分布：分片、再平衡与热点

**分片（Sharding / Partitioning）是横向扩展的唯一手段**，但它带来三个连环难题：

1. **分片算法的选择**
   - **哈希分片**：`hash(key) % N`——分布均匀，但**扩容时 N 变化会导致几乎全部数据迁移**，这是灾难。
   - **一致性哈希（Consistent Hashing）**：扩容只迁移 `1/N` 数据，但需引入**虚拟节点（vnode）**来解决数据倾斜。
   - **范围分片（Range）**：按 key 区间划分，支持高效范围扫描（scan），但**顺序写入会造成尾部热点**（如以时间戳为 key，所有写入都打在最后一个分片）。
   - **中心化分片表**：由 Master 维护 `Shard → Node` 映射表，最灵活（可精细调度），代价是元数据服务的复杂度。

2. **再平衡（Rebalancing）的代价**：加入新节点、下线旧节点、副本修复都要搬数据。**在线搬数据时如何不影响正常读写**——迁移会抢占磁盘 I/O 和网络带宽，稍有不慎就是全站延迟飙升。生产上必须做限流（throttle）、按时间窗调度、优先级队列。

3. **热点（Hotspot）**：数据分布均匀 ≠ 访问分布均匀。一个爆款商品的 key、一个明星的用户 ID，会把单个分片打死。需要热点探测 + 分片分裂（split）+ 读缓存 + key 加随机后缀打散等组合手段。

### 2.3 副本一致性与共识：为什么必须用 Raft/Paxos

多副本是可靠性的来源，也是一致性问题的来源。三种复制策略：

| 策略 | 机制 | 优点 | 缺点 |
|------|------|------|------|
| **同步复制** | 全部副本 ACK 才返回成功 | 不丢数据 | 一个副本慢/挂 → 写入阻塞，可用性差 |
| **异步复制** | 主副本落盘即返回 | 延迟最低 | 主挂 → **已确认的数据可能丢失** |
| **半同步 / 多数派（Quorum）** | `W + R > N` 时可读到最新 | 兼顾可靠与可用 | 实现复杂，需 Leader 选举 |

**多数派（Quorum）是现代分布式存储的事实标准**：N=3 时 W=2、R=2，可容忍 1 个节点故障。

而**共识算法（Raft / Multi-Paxos）解决的是"多数派 + Leader 选举 + 日志顺序"的完整问题**。为什么不能手写主从切换？因为会遇到：

- **脑裂（Split Brain）**：网络分区后两个节点都认为自己是主，双写导致数据分叉。
- **旧主复活**：老 Leader 网络恢复后带着过期数据回来，必须能被识别并降级（Raft 用 `term` 任期号解决）。
- **日志空洞与截断**：新 Leader 上任后如何裁剪 Follower 上多余的未提交日志。

这些边界条件极其反直觉，**"自己写一套主从切换"是分布式存储中最经典的踩坑点**，业界共识是：**共识算法必须用经过验证的成熟实现（Raft 库），绝不自研**。

### 2.4 故障检测与自愈：包括"静默数据损坏"

- **故障检测的根本困难**：**你无法区分"节点挂了"和"节点很慢/网络抖动"**（这是 FLP 不可能定理的工程投影）。心跳超时设短了误判频繁触发不必要的切换（切换本身有代价），设长了故障恢复慢。生产上常用 φ-Accrual 自适应故障检测替代固定阈值。
- **副本自动修复**：检测到副本数不足要自动补齐，但要防止"抖动引发的雪崩式重建"——大量重建会打满网络，反而拖垮集群（AWS S3 与 GitHub 都曾发生此类连锁故障）。
- **静默数据损坏（Silent Data Corruption / Bit Rot）**：磁盘可能返回"读取成功但内容已损坏"的数据，且不报错。**这是存储系统独有的、最阴险的问题**——它会安静地毒害所有副本（如果修复时从坏副本复制）。必须依靠：
  - 端到端校验和（CRC32C / xxHash），写入时算、读取时校验；
  - 后台巡检（Scrubbing）周期性全量校验；
  - 修复时以校验和为准，而非"以主副本为准"。

### 2.5 元数据管理：容易被忽视的真正瓶颈

元数据（对象位置、目录树、分片映射、副本状态）的特征是：**量大、访问极频繁、且要求强一致**。

- **HDFS 的经典教训**：NameNode 将全部元数据放内存，单点内存成为集群规模上限（约 1 亿文件即触顶），且是单点故障源。这直接催生了 Federation、HDFS Router、以及 Ozone 的重新设计。
- **难点**：元数据操作往往需要**事务**（如 `rename` 要原子地改变整棵子树的归属），而分布式事务代价昂贵。
- 现代方案倾向于：把元数据本身也做成分布式 KV（Ozone 用 RocksDB + Ratis、JuiceFS 用 Redis/TiKV），或彻底去中心化（Ceph 的 CRUSH 算法**用计算代替查表**，客户端算出数据位置，无需元数据服务）。

### 2.6 性能、尾延迟与成本

- **尾延迟（Tail Latency）放大效应**：一次请求扇出到 3 个副本，整体延迟取决于**最慢的那个**。若单副本 P99 = 100ms，扇出 3 个后整体 P99 会显著劣化。解决手段：Hedged Request（备份请求）、Tied Request、请求对冲与快速失败。
- **写放大（Write Amplification）**：LSM-Tree 的 Compaction 会反复重写数据，实际写入磁盘量是逻辑写入的 10~30 倍，直接消耗 SSD 寿命与 I/O 带宽。
- **成本**：3 副本意味着 **200% 的存储开销**。EB 级规模下这是天文数字，因此冷数据必须用**纠删码（Erasure Coding）**——但 EC 的重建代价高、CPU 开销大、小文件不友好，需要分层策略。
- **小文件问题**：海量小文件会让元数据量爆炸（10 亿个 4KB 文件的元数据可能比数据本身还大）。通用解法是合并存储（SeaweedFS 的 Haystack 思路、HDFS 的 HAR/SequenceFile）。

### 2.7 难点总览与优先级

| 优先级 | 难点 | 是否有成熟解法 | 工程建议 |
|:---:|------|:---:|------|
| **P0** | 一致性/可用性取舍（2.1） | 有理论（CAP/PACELC）无万能解 | 按数据分级定策略，写进设计文档 |
| **P0** | 副本共识与脑裂（2.3） | ✅ 有（Raft/Paxos） | **直接用成熟库，禁止自研** |
| **P0** | 数据不丢（WAL + fsync） | ✅ 有 | 严守"先写日志再改数据" |
| **P1** | 数据分布与再平衡（2.2） | ✅ 有（一致性哈希/分片表） | 迁移必须限流 |
| **P1** | 元数据瓶颈（2.5） | 部分（KV 化 / CRUSH） | 早期就别把元数据放单机内存 |
| **P1** | 静默损坏（2.4） | ✅ 有（校验和 + 巡检） | 端到端 CRC 是底线 |
| **P2** | 尾延迟与写放大（2.6） | 有工程手段 | 上线后针对性优化 |
| **P2** | 成本优化（EC / 分层） | ✅ 有 | 规模上来后再做 |

## 3. 整体设计思路与实现路径

### 3.1 核心设计哲学：四条第一原则

在写任何代码之前，先确立四条贯穿全局的原则。所有具体设计都是这四条的推论：

| 原则 | 含义 | 具体体现 |
|------|------|----------|
| **① 假设一切都会失败** | 硬件故障是常态而非异常 | 多副本、自动故障转移、幂等重试、超时控制 |
| **② 数据与元数据分离** | 控制面（轻、强一致）与数据面（重、可并行）解耦 | Master 只管调度，数据直接客户端↔DataNode |
| **③ 追加优于覆盖** | 顺序写远快于随机写，且崩溃语义更简单 | WAL、LSM-Tree、不可变对象（immutable object） |
| **④ 能力做减法换扩展性** | 放弃不必要的语义以换取扩展能力 | 对象存储放弃 rename、KV 放弃跨行事务 |

### 3.2 分层参考架构

一个完整的分布式存储系统可以稳定地划分为五层。**这个分层是通用骨架**，无论对象存储还是 KV 存储都适用：

```
┌──────────────────────────────────────────────────────────────┐
│  ① 接入层 (Access Layer)                                     │
│     SDK / S3 兼容 HTTP API / gRPC / POSIX FUSE 挂载          │
│     职责：协议解析、鉴权、限流、请求路由、客户端缓存         │
└───────────────────────┬──────────────────────────────────────┘
                        │
┌───────────────────────▼──────────────────────────────────────┐
│  ② 元数据层 (Metadata / Control Plane)   —— 强一致，小而稳    │
│     分片映射表 · 副本位置 · 目录树 · 集群成员 · 心跳状态      │
│     实现：Raft 集群 (3/5 节点) 或 外置 etcd/ZooKeeper         │
│     职责：定位、分配、调度、故障决策、负载均衡决策           │
└───────────────────────┬──────────────────────────────────────┘
                        │  (只返回"去哪里读写"，不经手数据)
┌───────────────────────▼──────────────────────────────────────┐
│  ③ 数据分布层 (Placement)                                     │
│     一致性哈希 / Range 分片 / CRUSH 算法 / 中心化分片表        │
│     职责：Key → Shard → Node 的映射，副本放置策略（机架感知） │
└───────────────────────┬──────────────────────────────────────┘
                        │
┌───────────────────────▼──────────────────────────────────────┐
│  ④ 复制与一致性层 (Replication & Consensus)                   │
│     Raft / Multi-Paxos / 主从半同步 / Quorum(NWR) / 纠删码     │
│     职责：多副本一致、Leader 选举、日志复制、成员变更         │
└───────────────────────┬──────────────────────────────────────┘
                        │
┌───────────────────────▼──────────────────────────────────────┐
│  ⑤ 存储引擎层 (Storage Engine)  —— 单机之内的事               │
│     WAL + MemTable + SSTable (LSM) / B+Tree / 裸块管理        │
│     校验和 · 压缩 · Compaction · 缓存 · fsync 策略            │
└──────────────────────────────────────────────────────────────┘
        ⑥ 横切面：监控告警 · 巡检修复 · 扩缩容 · 多租户 · 加密
```

**关键设计要点：控制面与数据面必须分离。** 元数据服务只回答"数据在哪"，随后客户端**直连** DataNode 传输数据。若让 Master 中转数据，它必然成为带宽瓶颈。这是 GFS/HDFS 奠定的经典范式，也是所有现代存储系统的共同选择。

### 3.3 关键设计决策一：数据分布策略

```
方案 A：一致性哈希 + 虚拟节点        方案 B：中心化分片表
┌─────────────────────────┐         ┌──────────────────────┐
│   环形哈希空间 0~2^32    │         │ Shard-1 → [A,B,C]    │
│  vnode 分散在环上        │         │ Shard-2 → [B,C,D]    │
│  key 顺时针找到第一个    │         │ Shard-3 → [C,D,A]    │
│  ✅ 无需中心化元数据      │         │ ✅ 调度精细、可人工干预│
│  ✅ 扩容只迁 1/N          │         │ ✅ 支持分片分裂/合并  │
│  ❌ 不支持范围扫描        │         │ ❌ 需维护元数据一致性 │
│  ❌ 精细调度困难          │         │ ❌ 分片数多时表变大   │
└─────────────────────────┘         └──────────────────────┘
     Cassandra / Dynamo                 TiKV(PD) / HDFS / Ozone
```

**选型决策树**：

1. 需要 **范围扫描（scan）/ 有序遍历** → 必须 Range 分片（TiKV 模式）。
2. 纯 KV 点查、追求去中心化与运维简单 → 一致性哈希（Cassandra 模式）。
3. 需要精细负载调度、热点自动分裂 → 中心化分片表 + 调度器（PD 模式，**功能最强，也最推荐给自研项目**）。
4. 不想维护元数据服务、能接受计算开销 → CRUSH 伪随机算法（Ceph 模式）。

**副本放置必须做故障域隔离**：3 副本不能落在同一台物理机、同一机架、同一交换机下。标准策略（HDFS）是：副本 1 在本机/本机架，副本 2、3 在另一机架的不同节点——兼顾写入带宽与机架级容灾。

### 3.4 关键设计决策二：一致性协议

```
写入路径的三种一致性强度
────────────────────────────────────────────────────────
① 强一致（Raft 多数派）
   Client → Leader → 并行复制 → 收到 (N/2+1) ACK → 返回成功
   ✅ 线性一致，Leader 挂了不丢已提交数据
   ❌ 每次写至少一个 RTT + 一次 fsync；跨机房延迟敏感

② Quorum NWR（无 Leader）
   N=3, W=2, R=2 → W+R>N 保证读到最新版本
   冲突用 版本向量(Vector Clock) / LWW(最后写入胜) 解决
   ✅ 高可用、无选举停顿   ❌ 需处理冲突，客户端逻辑变重

③ 主从异步复制
   Client → Master 落盘 → 立即返回 → 后台复制到 Slave
   ✅ 延迟最低   ❌ 故障可能丢失最后一段数据（RPO > 0）
```

**推荐做法（生产验证过的组合拳）**：

- **元数据层用 Raft**：数据量小、要求强一致，Raft 的性能开销可接受，且省去所有脑裂烦恼。
- **数据层按业务分级**：热数据/关键数据用 Raft 或半同步多数派；冷数据、日志类数据可用异步复制 + 纠删码降本。
- **给用户提供可调一致性**：像 Cassandra 那样把 `ONE / QUORUM / ALL` 作为**每次请求的参数**开放出去，把取舍权交给业务方，这是最优雅的工程解法。

### 3.5 关键设计决策三：单机存储引擎（LSM vs B+Tree）

分布式存储的性能地基仍在单机引擎。两大流派：

| 维度 | **LSM-Tree** | **B+Tree** |
|------|--------------|------------|
| 写入 | ⭐ 顺序追加，写吞吐极高 | 随机写、页分裂，较慢 |
| 点读 | 较慢（需查多层 + 布隆过滤器） | ⭐ 稳定 O(log n) |
| 范围扫描 | 良好（需多路归并） | ⭐ 优秀（叶子链表） |
| 空间放大 | 有（多版本未合并） | 有（页碎片） |
| 写放大 | 高（Compaction 反复重写） | 中等 |
| 代表 | RocksDB、LevelDB、HBase、Cassandra | InnoDB、BoltDB、LMDB |

**存储系统绝大多数选 LSM-Tree**，因为分布式场景下写入吞吐与顺序 I/O 友好性更关键。

LSM 写入路径（这是必须刻进脑子的核心结构）：

```
写请求
  │
  ├──► 1. WAL 顺序追加 + fsync   ← ★ 崩溃恢复的唯一保障
  │
  └──► 2. MemTable（内存跳表 SkipList，有序）
             │  写满阈值（如 64MB）
             ▼
        Immutable MemTable → 后台 Flush
             │
             ▼
        L0 SSTable（磁盘，不可变、有序、带布隆过滤器 + 稀疏索引）
             │  Compaction（分层归并，去重、清理墓碑）
             ▼
        L1 → L2 → ... → Ln （越深越大越冷）

读请求：MemTable → Immutable → L0 → L1 ... （布隆过滤器快速跳过）
```

**"先写 WAL 再改内存"是存储系统的铁律**：宕机后重放 WAL 即可恢复 MemTable。`fsync` 是否每次调用，是"性能 vs 数据安全"最直接的旋钮——组提交（Group Commit）是标准折中：攒一批请求做一次 fsync，用微小延迟换数吞吐量数量级提升。

### 3.6 实现路径：四阶段渐进式演进

自研分布式存储切忌一开始就追求完备。建议按下面四阶段推进，**每个阶段都是一个可运行、可验证的完整系统**：

| 阶段 | 目标 | 交付内容 | 验证标准 |
|:---:|------|----------|----------|
| **阶段一**<br>单机可靠 | 数据不丢 | 单机 KV 引擎：WAL + MemTable + SSTable + CRC 校验 | kill -9 后数据可完整恢复 |
| **阶段二**<br>多副本 | 单点故障不影响服务 | 引入 Raft（3 节点），Leader 选举 + 日志复制 | 杀掉 Leader，服务在秒级恢复且不丢已确认写入 |
| **阶段三**<br>可扩展 | 容量与吞吐随节点线性增长 | 分片（Region）+ 元数据服务 + 客户端路由 + 在线扩容迁移 | 新增节点后自动均衡；迁移期间读写不中断 |
| **阶段四**<br>生产级 | 稳定、可观测、低成本 | 巡检修复、热点分裂、纠删码、多租户、监控告警、限流 | 混沌测试（随机杀节点/断网/塞盘）下 SLA 达标 |

> **务实提醒**：阶段三的"在线迁移不中断服务"是难度陡增点——它要求分片路由、Raft 成员变更、客户端重试三者精确配合。这也是自研项目最常搁浅的位置。若无强诉求，**优先选用成熟系统（第 4 节），把精力留给业务**。

### 3.7 数据可靠性设计：从 3 副本到纠删码

```
三副本 (3-Replica)                纠删码 EC(6,3) — Reed-Solomon
┌────┬────┬────┐                 ┌──┬──┬──┬──┬──┬──┬──┬──┬──┐
│ D  │ D  │ D  │                 │D1│D2│D3│D4│D5│D6│P1│P2│P3│
└────┴────┴────┘                 └──┴──┴──┴──┴──┴──┴──┴──┴──┘
存储开销：300%                     存储开销：150%
容错：任意 1 坏(可容 2)            容错：任意 3 块损坏可恢复
恢复：直接拷贝（快、省 CPU）        恢复：需读 6 块重算（慢、耗 CPU/网络）
读延迟：低                         读延迟：正常读不受影响，降级读变慢
适合：热数据、小文件、低延迟       适合：冷数据、大文件、海量归档
```

**标准工程策略是分层**：热数据 3 副本保性能，数据冷却（如 30 天无访问）后由后台任务转为 EC 降本，元数据永远 3~5 副本强一致。这也是 S3 标准存储 / 低频访问 / 归档分层的底层逻辑。

## 5. Java 技术栈的具体实现

Java 在分布式存储领域有极深的积累——**HDFS、HBase、Cassandra、ZooKeeper、Ozone、Ratis、Alluxio、Ignite 全部由 Java 编写**。这意味着 Java 工程师既有大量可读的一流源码参照，也有成熟可复用的组件生态。

本节给出一个可落地的自研 KV 存储原型的完整实现路径。目标系统命名为 `MiniDFS`，能力对齐"阶段三"（多副本 + 分片 + 在线扩容）。

### 5.1 技术选型与整体骨架

| 层次 | 技术选型 | 理由 |
|------|----------|------|
| 网络通信 | **Netty 4**（或 gRPC-Java） | 异步非阻塞、零拷贝支持、Java 存储系统通用选择 |
| 序列化 | Protobuf / Kryo | 紧凑、跨语言、向前兼容 |
| 共识协议 | **SOFAJRaft** 或 **Apache Ratis** | 生产验证，避免自研共识（2.3 节铁律） |
| 单机引擎 | **RocksDB (JNI)**，学习期可手写 LSM | 免去 Compaction 等深水区工作 |
| 元数据 | 自建 Raft 组 或 外置 **etcd** | 强一致、支持 watch |
| 校验 | CRC32C（`java.util.zip.CRC32C`，JDK 9+） | 硬件加速，端到端校验 |
| 纠删码 | Backblaze `JavaReedSolomon` / ISA-L | 冷数据降本 |
| 监控 | Micrometer + Prometheus + Grafana | 存储系统必须可观测 |
| 部署 | Spring Boot（管理面）+ 独立进程（数据面） | 管理面用 Spring 提效，数据面避免框架开销 |

工程模块划分：

```
minidfs/
├── minidfs-common/        协议定义(Protobuf)、CRC工具、配置、异常体系
├── minidfs-client/        SDK：路由缓存、重试、故障转移、读写并发
├── minidfs-meta/          元数据服务：分片表、成员管理、心跳、调度器(Raft组)
├── minidfs-datanode/      数据节点：Netty服务、存储引擎、Raft状态机、巡检
└── minidfs-engine/        单机引擎：WAL、MemTable、SSTable、Compaction
```

### 5.2 实现一：数据分布（一致性哈希 + 虚拟节点）

分片定位是所有请求的第一步，要求**无锁、纳秒级、结果与元数据服务完全一致**。

```java
/**
 * 一致性哈希路由器，通过虚拟节点解决数据倾斜问题。
 * 线程安全依赖 volatile 的不可变 TreeMap 快照，读路径完全无锁。
 */
public class ConsistentHashRouter {

    private static final int VIRTUAL_NODES_PER_NODE = 160;

    private volatile NavigableMap<Long, String> ring = new TreeMap<>();

    /** 重建哈希环。节点变更（上线/下线）时调用，通过整体替换保证读侧无锁且视图一致。 */
    public synchronized void rebuild(Collection<String> physicalNodes) {
        NavigableMap<Long, String> newRing = new TreeMap<>();
        for (String node : physicalNodes) {
            for (int i = 0; i < VIRTUAL_NODES_PER_NODE; i++) {
                newRing.put(hash(node + "#VN" + i), node);
            }
        }
        this.ring = newRing;
    }

    /** 为 key 选出 replicaCount 个互不相同的物理节点，第一个为主副本。 */
    public List<String> route(String key, int replicaCount) {
        NavigableMap<Long, String> snapshot = this.ring;
        if (snapshot.isEmpty()) {
            throw new IllegalStateException("hash ring is empty, no available node");
        }
        int distinctNodes = (int) snapshot.values().stream().distinct().count();
        int expected = Math.min(replicaCount, distinctNodes);   // 节点不足时降级，避免死循环

        List<String> result = new ArrayList<>(expected);
        long cursor = hash(key);
        int scanned = 0;
        while (result.size() < expected && scanned++ <= snapshot.size()) {
            Map.Entry<Long, String> entry = snapshot.ceilingEntry(cursor);
            if (entry == null) {
                entry = snapshot.firstEntry();       // 环形回绕
            }
            if (!result.contains(entry.getValue())) {
                result.add(entry.getValue());        // 去重：同一物理节点只放一个副本
            }
            cursor = entry.getKey() + 1;
        }
        return result;
    }

    private long hash(String raw) {
        byte[] digest = DigestUtils.md5(raw);
        return ((long) (digest[3] & 0xFF) << 24)
                | ((long) (digest[2] & 0xFF) << 16)
                | ((long) (digest[1] & 0xFF) << 8)
                | (digest[0] & 0xFF);
    }
}
```

**要点说明**：

1. `VIRTUAL_NODES_PER_NODE = 160` 是经验值（Cassandra 早期默认 256、Dynamo 用数百）。虚拟节点越多分布越均匀，但环越大、内存与查找开销越高。
2. 用 `volatile` + 整体替换 `TreeMap` 实现读写分离，避免读路径加锁——这是高频路径的常用优化手法。
3. 副本必须去重（一个 key 的 3 个副本不能落在同一物理节点），生产上还需叠加**机架感知**：跳过与已选副本同机架的节点。

### 5.3 实现二：副本一致性（SOFAJRaft 状态机）

**这是自研中最不该自己写、也最该学会用的部分。** 用 SOFAJRaft 只需实现"状态机"，把日志应用到本地存储引擎即可。

```java
/**
 * 分片级 Raft 状态机：把已达成共识的日志应用到本地存储引擎。
 * onApply 中的操作必须是确定性且幂等的，否则各副本状态会分叉。
 */
public class ShardStateMachine extends StateMachineAdapter {

    private final StorageEngine engine;
    private final AtomicLong appliedIndex = new AtomicLong(0);
    private volatile boolean isLeader = false;

    public ShardStateMachine(StorageEngine engine) {
        this.engine = engine;
    }

    @Override
    public void onApply(Iterator iterator) {
        while (iterator.hasNext()) {
            WriteCommand command;
            Closure done = iterator.done();
            if (done != null) {
                // Leader 本地路径：直接复用内存中的请求对象，省一次反序列化
                command = ((WriteClosure) done).getCommand();
            } else {
                // Follower 或重放路径：从日志字节反序列化
                command = ProtostuffSerializer.deserialize(
                        iterator.getData().array(), WriteCommand.class);
            }

            try {
                switch (command.getType()) {
                    case PUT -> engine.put(command.getKey(), command.getValue());
                    case DELETE -> engine.delete(command.getKey());
                    default -> throw new IllegalArgumentException(
                            "unknown command type: " + command.getType());
                }
                appliedIndex.set(iterator.getIndex());
                if (done != null) {
                    ((WriteClosure) done).setResult(true);
                    done.run(Status.OK());
                }
            } catch (Exception e) {
                // 状态机异常必须让本节点退出复制，绝不能跳过日志继续 apply
                iterator.setErrorAndRollback(1, new Status(-1, "apply failed: %s", e.getMessage()));
                return;
            }
            iterator.next();
        }
    }

    @Override
    public void onSnapshotSave(SnapshotWriter writer, Closure done) {
        String snapshotPath = writer.getPath() + File.separator + "data.snapshot";
        ThreadPoolUtil.runInThread(() -> {
            try {
                engine.createCheckpoint(snapshotPath);
                writer.addFile("data.snapshot");
                done.run(Status.OK());
            } catch (Exception e) {
                done.run(new Status(RaftError.EIO, "snapshot save failed: %s", e.getMessage()));
            }
        });
    }

    @Override
    public boolean onSnapshotLoad(SnapshotReader reader) {
        if (isLeader) {
            return false;   // Leader 不应加载快照
        }
        try {
            engine.restoreFromCheckpoint(reader.getPath() + File.separator + "data.snapshot");
            return true;
        } catch (Exception e) {
            return false;
        }
    }

    @Override
    public void onLeaderStart(long term) {
        this.isLeader = true;
        super.onLeaderStart(term);
    }

    @Override
    public void onLeaderStop(Status status) {
        this.isLeader = false;
        super.onLeaderStop(status);
    }
}
```

写入入口（区分 Leader / Follower，并处理转发）：

```java
public void put(String key, byte[] value, CompletableFuture<Boolean> future) {
    if (!node.isLeader()) {
        // 转发给 Leader，或直接返回重定向让客户端刷新路由缓存
        forwardToLeader(key, value, future);
        return;
    }
    WriteCommand command = WriteCommand.put(key, value);
    WriteClosure closure = new WriteClosure(command, future);
    Task task = new Task();
    task.setData(ByteBuffer.wrap(ProtostuffSerializer.serialize(command)));
    task.setDone(closure);
    node.apply(task);   // 提交给 Raft，多数派 ACK 后回调 onApply
}
```

**Raft 落地的四个高频坑**：

| 坑 | 现象 | 解法 |
|---|------|------|
| `onApply` 中做非确定性操作 | 各副本状态分叉，数据不一致 | 禁止在状态机内用 `System.currentTimeMillis()`、随机数、外部 RPC；时间戳应由 Leader 写入日志 |
| 快照太少/太多 | 太少→重启回放极慢；太多→I/O 抖动 | 按日志条数 + 时间双阈值触发，避开业务高峰 |
| 忽略读一致性 | Follower 读到过期数据 | 读走 Leader，或用 ReadIndex / Lease Read 优化 |
| 单 Raft 组承载全部数据 | Leader 成为瓶颈，无法扩展 | **Multi-Raft**：每个分片一个 Raft 组，Leader 分散到各节点 |

> **Multi-Raft 是分布式存储可扩展性的关键设计**（TiKV 的核心）。单 Raft 组的吞吐上限就是单机上限；分成上千个 Raft 组后，各组 Leader 均匀分布，整体吞吐随节点线性增长。

### 5.4 实现三：单机存储引擎（LSM 核心骨架）

生产上直接用 RocksDB，但**亲手写一遍 LSM 是理解存储系统最有效的方式**。

```java
/**
 * 简化版 LSM 存储引擎：WAL 保证崩溃不丢，MemTable 提供有序内存写入，
 * 写满后 flush 为不可变 SSTable。省略了 Compaction 与布隆过滤器。
 */
public class LsmStorageEngine implements StorageEngine {

    private static final long MEMTABLE_THRESHOLD_BYTES = 64L * 1024 * 1024;

    private final Path dataDir;
    private final WriteAheadLog wal;
    private final List<SsTable> ssTables = new CopyOnWriteArrayList<>();
    private volatile ConcurrentSkipListMap<byte[], byte[]> memTable =
            new ConcurrentSkipListMap<>(Arrays::compare);
    private final AtomicLong memTableBytes = new AtomicLong(0);
    private final ReentrantLock flushLock = new ReentrantLock();

    public LsmStorageEngine(Path dataDir) throws IOException {
        this.dataDir = dataDir;
        this.wal = new WriteAheadLog(dataDir.resolve("wal"));
        recover();
    }

    @Override
    public void put(byte[] key, byte[] value) throws IOException {
        wal.append(WalRecord.put(key, value));          // 1. 先写日志（含 CRC + fsync 策略）
        memTable.put(key, value);                        // 2. 再改内存
        long size = memTableBytes.addAndGet(key.length + value.length);
        if (size >= MEMTABLE_THRESHOLD_BYTES) {
            triggerFlush();
        }
    }

    @Override
    public byte[] get(byte[] key) throws IOException {
        byte[] value = memTable.get(key);                 // 新数据优先
        if (value != null) {
            return TOMBSTONE == value ? null : value;
        }
        for (int i = ssTables.size() - 1; i >= 0; i--) {  // 从新到旧查磁盘
            SsTable table = ssTables.get(i);
            if (!table.mayContain(key)) {                 // 布隆过滤器快速跳过
                continue;
            }
            value = table.get(key);
            if (value != null) {
                return TOMBSTONE == value ? null : value;
            }
        }
        return null;
    }

    @Override
    public void delete(byte[] key) throws IOException {
        wal.append(WalRecord.delete(key));
        memTable.put(key, TOMBSTONE);                     // 墓碑标记，Compaction 时物理清除
    }

    /** 将当前 MemTable 冻结并异步落盘为 SSTable，随后可安全截断对应 WAL。 */
    private void triggerFlush() {
        flushLock.lock();
        try {
            if (memTableBytes.get() < MEMTABLE_THRESHOLD_BYTES) {
                return;
            }
            ConcurrentSkipListMap<byte[], byte[]> frozen = this.memTable;
            this.memTable = new ConcurrentSkipListMap<>(Arrays::compare);
            this.memTableBytes.set(0);
            long walMark = wal.currentOffset();
            FLUSH_EXECUTOR.submit(() -> {
                try {
                    SsTable table = SsTable.writeFrom(frozen, nextSsTablePath());
                    ssTables.add(table);
                    wal.truncateBefore(walMark);          // 数据已持久化，日志可回收
                } catch (IOException e) {
                    log.error("flush memtable failed", e);
                }
            });
        } finally {
            flushLock.unlock();
        }
    }

    /** 启动时重放 WAL，把上次未 flush 的写入恢复到 MemTable。 */
    private void recover() throws IOException {
        loadExistingSsTables();
        wal.replay(record -> {
            if (record.isDelete()) {
                memTable.put(record.getKey(), TOMBSTONE);
            } else {
                memTable.put(record.getKey(), record.getValue());
            }
        });
    }
}
```

WAL 的关键实现（**数据不丢的最后防线**）：

```java
/** 顺序追加日志。每条记录携带 CRC32C，重放时校验，遇到损坏记录即停止（尾部可能是半条写入）。 */
public class WriteAheadLog {

    private final FileChannel channel;
    private final ByteBuffer buffer = ByteBuffer.allocateDirect(1 << 20);
    private final SyncPolicy syncPolicy;

    public synchronized void append(WalRecord record) throws IOException {
        byte[] payload = record.encode();
        CRC32C crc = new CRC32C();
        crc.update(payload);

        ByteBuffer frame = ByteBuffer.allocate(4 + 4 + payload.length);
        frame.putInt(payload.length);
        frame.putInt((int) crc.getValue());
        frame.put(payload);
        frame.flip();
        channel.write(frame);

        switch (syncPolicy) {
            case EVERY_WRITE -> channel.force(false);          // 最安全，最慢
            case GROUP_COMMIT -> groupCommitter.requestSync(); // 攒批 fsync，推荐
            case OS_FLUSH -> { }                               // 最快，宕机可能丢
        }
    }
}
```

**三种 fsync 策略的量级差异（SATA SSD 参考值）**：

| 策略 | 写入 TPS | 宕机丢数据窗口 | 适用 |
|------|:---:|:---:|------|
| 每次 fsync | ~1K~5K | 0 | 金融、元数据 |
| 组提交（1~10ms 批量） | ~50K~200K | ≤10ms（已 ACK 的仍安全） | ⭐ 通用推荐 |
| 交给 OS 刷盘 | ~500K+ | 数秒 | 缓存、可重建数据 |

> **组提交为何既快又安全**：多个并发写请求共享一次 `fsync`，但每个请求都要等到 `fsync` 完成后才返回成功。因此"已返回成功的数据"依然保证在盘上——牺牲的只是单请求延迟（增加几毫秒），换来吞吐量的数量级提升。

### 5.5 实现四：高性能数据传输（Netty + 零拷贝）

存储系统的数据面要搬运海量字节，**JVM 堆内外的内存拷贝是主要性能杀手**。Java 侧有三张牌：

| 技术 | API | 效果 | 适用 |
|------|-----|------|------|
| **堆外直接内存** | `ByteBuffer.allocateDirect` / Netty `PooledByteBufAllocator` | 避免堆内→堆外拷贝，减少 GC 压力 | 所有网络收发缓冲 |
| **sendfile 零拷贝** | `FileChannel.transferTo` / Netty `DefaultFileRegion` | 文件→网卡不经用户态，CPU 与内存带宽大降 | 大对象/大文件下载 |
| **mmap 内存映射** | `FileChannel.map` | 随机读免系统调用，页缓存直接可见 | 索引文件、小随机读 |

```java
/**
 * 数据节点读服务：对大对象走 sendfile 零拷贝，对小对象走内存池化缓冲。
 * 阈值 64KB 是经验值——零拷贝在小数据上收益不足，反而增加系统调用开销。
 */
public class BlockReadHandler extends SimpleChannelInboundHandler<ReadRequest> {

    private static final long ZERO_COPY_THRESHOLD = 64 * 1024L;

    @Override
    protected void channelRead0(ChannelHandlerContext ctx, ReadRequest request) throws Exception {
        BlockLocation location = blockManager.locate(request.getBlockId());
        long length = location.getLength();

        if (!checksumVerifier.verify(location)) {
            ctx.writeAndFlush(ReadResponse.corrupted(request.getBlockId()));
            repairScheduler.submitRepair(request.getBlockId());   // 触发副本修复
            return;
        }

        if (length >= ZERO_COPY_THRESHOLD) {
            RandomAccessFile file = new RandomAccessFile(location.getFile(), "r");
            ctx.write(ReadResponse.header(request.getBlockId(), length));
            // FileRegion 底层走 sendfile，数据不进入 JVM 堆
            ctx.writeAndFlush(new DefaultFileRegion(file.getChannel(), location.getOffset(), length))
               .addListener(f -> file.close());
        } else {
            ByteBuf buf = ctx.alloc().directBuffer((int) length);
            blockManager.readInto(location, buf);
            ctx.writeAndFlush(ReadResponse.of(request.getBlockId(), buf));
        }
    }
}
```

**Netty 服务端配置要点**：

```java
ServerBootstrap bootstrap = new ServerBootstrap()
```

### 5.6 实现五：故障检测与副本自愈

```java
/**
 * 基于 φ-Accrual 思想的自适应故障检测：用心跳到达间隔的历史分布计算"怀疑度"，
 * 相比固定超时阈值，能自动适应网络抖动，显著降低误判率（Cassandra 采用同类算法）。
 */
public class PhiAccrualFailureDetector {

    private static final double PHI_SUSPECT_THRESHOLD = 8.0;
    private final Map<String, DescriptiveStatistics> intervalHistory = new ConcurrentHashMap<>();
    private final Map<String, Long> lastHeartbeat = new ConcurrentHashMap<>();

    public void onHeartbeat(String nodeId) {
        long now = System.nanoTime();
        Long previous = lastHeartbeat.put(nodeId, now);
        if (previous != null) {
            intervalHistory.computeIfAbsent(nodeId, k -> new DescriptiveStatistics(1000))
                           .addValue((now - previous) / 1_000_000.0);
        }
    }

    /** 返回怀疑度 φ。φ 越大越可能已宕机；φ=8 约等于误判率 10^-8。 */
    public double phi(String nodeId) {
        Long last = lastHeartbeat.get(nodeId);
        DescriptiveStatistics stats = intervalHistory.get(nodeId);
        if (last == null || stats == null || stats.getN() < 10) {
            return 0.0;
        }
        double elapsedMs = (System.nanoTime() - last) / 1_000_000.0;
        double mean = stats.getMean();
        double stdDev = Math.max(stats.getStandardDeviation(), 1.0);
        double probability = 1.0 - normalCdf(elapsedMs, mean, stdDev);
        return -Math.log10(Math.max(probability, 1e-12));
    }

    public boolean isSuspected(String nodeId) {
        return phi(nodeId) > PHI_SUSPECT_THRESHOLD;
    }
}
```

副本修复调度器的**三条防雪崩规则**（血泪经验）：

```java
/**
 * 副本修复调度：检测到副本数不足时补齐。三条限制共同防止"故障引发的重建风暴"
 * 把集群网络与磁盘打满，从而导致更大范围的连锁故障。
 */
public class ReplicaRepairScheduler {

    private static final int MAX_CONCURRENT_REPAIR_PER_NODE = 2;   // ① 并发上限
    private static final long REPAIR_BANDWIDTH_BYTES_PER_SEC = 50L * 1024 * 1024;  // ② 带宽限流
    private static final Duration SUSPECT_GRACE_PERIOD = Duration.ofMinutes(10);   // ③ 观察期

    private final RateLimiter bandwidthLimiter =
            RateLimiter.create(REPAIR_BANDWIDTH_BYTES_PER_SEC);

    public void onNodeSuspected(String nodeId) {
        // ③ 关键：不立即重建！先等观察期，避免网络抖动/重启触发无谓的全量搬迁
        scheduler.schedule(() -> {
            if (failureDetector.isSuspected(nodeId) && !membership.isBackOnline(nodeId)) {
                enqueueRepairTasks(nodeId);
            }
        }, SUSPECT_GRACE_PERIOD.toMinutes(), TimeUnit.MINUTES);
    }

    private void enqueueRepairTasks(String deadNode) {
        List<Shard> affected = metaService.findShardsOn(deadNode);
        // 按副本数从少到多排序：只剩 1 副本的最危险，优先修复
        affected.sort(Comparator.comparingInt(Shard::currentReplicaCount));
        for (Shard shard : affected) {
            repairQueue.offer(new RepairTask(shard, chooseTargetNode(shard)));
        }
    }
}
```

### 5.7 实现六：端到端校验与后台巡检

对抗静默数据损坏（2.4 节）的标准做法：

```java
/**
 * 后台巡检（Scrubbing）：周期性全量校验本地数据块的 CRC，
 * 发现损坏立即上报元数据服务，从健康副本重建，而非等到用户读取时才发现。
 */
@Scheduled(cron = "0 0 2 * * ?")   // 低峰期执行
public void scrubAllBlocks() {
    RateLimiter limiter = RateLimiter.create(20 * 1024 * 1024);   // 20MB/s，绝不影响线上
    for (BlockMeta block : blockManager.listLocalBlocks()) {
        limiter.acquire((int) block.getLength());
        long actual = computeCrc32c(block);
        if (actual != block.getExpectedCrc()) {
            log.error("silent corruption detected! block={} expected={} actual={}",
                    block.getId(), block.getExpectedCrc(), actual);
            metaService.reportCorruption(nodeId, block.getId());
            blockManager.quarantine(block);   // 隔离坏块，禁止再对外提供读
        }
        block.setLastScrubTime(System.currentTimeMillis());
    }
}
```

**校验的三个必备位置**（缺一不可）：

1. **写入时**：客户端计算 CRC 并随数据传输，DataNode 落盘前校验 → 防网络传输错误。
2. **读取时**：读出后校验再返回客户端 → 防磁盘静默损坏毒害业务。
3. **后台巡检**：周期性全量扫描 → 在冷数据被读取之前发现问题（冷数据可能几年不读，损坏会悄悄累积到所有副本都坏）。

| 问题 | 原因 | 解法 |
|------|------|------|
| **GC 停顿造成延迟毛刺** | 大堆 Full GC 停顿可达秒级，导致心跳超时被误判宕机、请求超时 | 用 **ZGC**（JDK 17+，停顿 <1ms）；堆不宜过大；把数据放堆外 |
| **堆外内存泄漏** | `DirectByteBuffer` 依赖 GC 回收，Netty `ByteBuf` 忘记 `release()` | 用 `PooledByteBufAllocator` + 引用计数检查；开 `-Dio.netty.leakDetection.level=paranoid` 压测 |
| **大对象进老年代** | 缓存大 byte[] 造成老年代碎片与频繁 GC | 数据缓冲一律用堆外；用 off-heap 缓存（如 Netty ByteBuf / Chronicle Map） |
| **心跳线程被 GC 拖累** | 心跳在 JVM 内，GC 时也会停 | 心跳超时阈值须大于最坏 GC 停顿；或用独立进程/内核态检测 |
| **序列化开销** | Java 原生序列化极慢且不安全 | 用 Protobuf / Kryo / Protostuff |
| **`fsync` 阻塞线程** | `channel.force()` 是阻塞系统调用 | 独立 I/O 线程池 + 组提交合并 |

推荐启动参数（数据节点，32GB 内存机器示例）：

```bash
java -XX:+UseZGC -XX:+ZGenerational \
     -Xms8g -Xmx8g \
     -XX:MaxDirectMemorySize=16g \
     -XX:+AlwaysPreTouch \
     -XX:+HeapDumpOnOutOfMemoryError \
     -Xlog:gc*,safepoint:file=/var/log/minidfs/gc.log:time,uptime:filecount=10,filesize=64m \
     -Dio.netty.allocator.type=pooled \
     -Dio.netty.maxDirectMemory=0 \
     -jar minidfs-datanode.jar
```

> 设计要点：**堆内存刻意保持小（8g）**，把大部分内存（16g 堆外 + 剩余留给 OS 页缓存）交给堆外与页缓存。这是 Java 存储系统的通用策略——HBase 的 BucketCache、Kafka 依赖页缓存都是这个思路。

### 5.10 完整读写流程串联（Java 视角时序）

```
【写入 PUT key=user:1001 value=...】

Client SDK
  │ ① 本地路由缓存查 shard（无缓存则问 MetaService，缓存 TTL 30s）
  │ ② 计算 CRC32C，Protobuf 编码
  ▼ Netty 长连接（连接池，按节点复用）
DataNode-A (Shard-7 Leader)
  │ ③ EventLoop 收包 → 解码 → 派发到业务线程池（不阻塞 EventLoop）
  │ ④ 校验 CRC，拒绝损坏请求
  │ ⑤ 构造 WriteCommand，node.apply(task) 提交 Raft
  │ ⑥ SOFAJRaft 并行复制到 B、C；本地写 WAL(组提交 fsync)
  │ ⑦ 收到 2/3 ACK → 触发 onApply → 写入 MemTable
  ▼ ⑧ Closure 回调 → CompletableFuture.complete(true)
Client 收到成功（典型 P99 ≈ 5~20ms，取决于 fsync 与网络）

【失败分支】
  · Leader 已切换 → 返回 NOT_LEADER + 新 Leader 地址 → SDK 刷新路由并重试
  · 多数派超时 → 返回 TIMEOUT（状态未知！）→ SDK 用幂等 requestId 重试
  · 磁盘满/坏 → 返回 IO_ERROR → MetaService 标记节点只读，调度器迁走分片
```

> **"超时状态未知"是分布式存储客户端设计的核心难点**：写超时后数据可能已提交也可能未提交。因此**所有写入必须携带幂等 ID（requestId）**，服务端做去重，才能安全重试。这一点在自研 SDK 时极易遗漏，却是数据正确性的关键。

## 6. 关键工程难题的实战解法

本节把第 2 节的难点逐一对应到可执行的解法，是全文最具操作性的部分。

### 6.1 在线扩容与数据再平衡（不停机）

```
目标：新增 Node-D，把部分分片迁移过去，全程不中断读写。

阶段 1  准备：MetaService 计算迁移计划（哪些分片 → D），生成任务队列
        原则：每轮只迁少量分片；优先迁走热点节点上的冷分片

阶段 2  数据预热：Node-D 作为 Learner(非投票成员) 加入 Raft 组
        ✅ 关键：Learner 只同步日志、不参与投票 → 不影响多数派计算
        → 全量快照传输（限流 50MB/s） + 增量日志追赶

阶段 3  切换：Learner 追平后（日志差距 < 阈值），提交 Raft 成员变更
        ConfChange: {A,B,C} → {A,B,D}，Raft 保证成员变更本身的一致性

阶段 4  清理：C 上的分片副本删除；MetaService 更新分片表并递增版本号
        → 客户端下次请求携带旧版本号时被告知刷新路由缓存
```

**四条铁律**：

| 规则 | 原因 |
|------|------|
| 迁移必须**限流** | 否则打满网络/磁盘，线上延迟飙升（最常见的扩容事故） |
| 用 **Learner 角色**预热 | 直接加为投票成员会改变多数派要求（3→4 需要 3 票），降低可用性 |
| 分片表带**版本号（Epoch）** | 客户端可能持有旧路由，服务端凭版本号识别并纠正，防止写到错误节点 |
| 迁移**可中断、可回滚** | 迁移中途出问题必须能立即停下且不留脏数据 |

### 6.2 热点分片的探测与治理

```java
/**
 * 热点探测：滑动窗口统计各分片 QPS 与流量，超阈值则上报调度器。
 * 治理手段按代价从低到高依次尝试，避免过早触发昂贵的分裂操作。
 */
public class HotspotDetector {

    private final Map<String, SlidingWindowCounter> shardQps = new ConcurrentHashMap<>();

    public void record(String shardId, int bytes) {
        shardQps.computeIfAbsent(shardId, k -> new SlidingWindowCounter(60))
                .increment(bytes);
    }

    @Scheduled(fixedDelay = 10_000)
    public void detect() {
        double clusterAvg = shardQps.values().stream()
                .mapToDouble(SlidingWindowCounter::qps).average().orElse(0);
        shardQps.forEach((shardId, counter) -> {
            if (counter.qps() > clusterAvg * 5 && counter.qps() > 1000) {
                schedulerClient.reportHotspot(shardId, counter.snapshot());
            }
        });
    }
}
```

治理手段阶梯（**按顺序尝试，先便宜后昂贵**）：

| 层级 | 手段 | 代价 | 见效 |
|:---:|------|:---:|:---:|
| 1 | 增加**只读副本**分摊读流量 | 低 | 快 |
| 2 | 客户端/服务端**本地缓存**热 key | 低 | 快 |
| 3 | 把热点分片的 **Leader 迁到空闲节点** | 中 | 快 |
| 4 | **分片分裂（Split）**：一分为二 | 高 | 中 |
| 5 | **Key 打散**：`user:1001` → `user:1001:{0-9}` 随机后缀 | 需改业务 | 彻底 |

> **注意**：单个超热 key（如秒杀商品库存）无法通过分裂解决——分片再细，同一个 key 仍在一个分片上。此时只能靠缓存、key 打散或业务层削峰。**这是存储层的能力边界，必须向业务方讲清楚。**

### 6.3 尾延迟优化：Hedged Request

```java
/**
 * 对冲请求：先发主副本，若在 P95 时间内未返回，向备副本发起第二个请求，取先返回者。
 * 用少量额外负载（约 5%）换取 P99 延迟的大幅下降（Google 实测可降低一个数量级）。
 */
public CompletableFuture<byte[]> hedgedRead(String key) {
    List<String> replicas = router.route(key, 3);
    CompletableFuture<byte[]> result = new CompletableFuture<>();

    CompletableFuture<byte[]> primary = sendRead(replicas.get(0), key);
    primary.whenComplete((v, e) -> { if (e == null) result.complete(v); });

    long hedgeDelayMs = latencyStats.percentile(95);   // 动态阈值，随集群状态自适应
    scheduler.schedule(() -> {
        if (!result.isDone()) {
            hedgedRequestCounter.increment();
            sendRead(replicas.get(1), key)
                .whenComplete((v, e) -> { if (e == null) result.complete(v); });
        }
    }, hedgeDelayMs, TimeUnit.MILLISECONDS);

    return result.orTimeout(2, TimeUnit.SECONDS);
}
```

其他尾延迟手段：**副本选择要感知负载**（优先读延迟低的副本）、**慢节点降级**（连续超时的节点临时踢出读路径）、**请求排队优先级**（用户请求优先于后台巡检/迁移任务）。

### 6.4 一致性问题的实战对照表

| 现象 | 根因 | 解法 |
|------|------|------|
| 写成功后立刻读不到 | 读到了未同步的 Follower | 读走 Leader；或用 ReadIndex；或客户端会话粘滞（读己之写） |
| 两个副本数据不同 | 异步复制 + 故障切换丢日志 | 改用 Raft 多数派；定期做副本一致性校验（Merkle Tree 比对） |
| 已确认的写入丢失 | 异步复制且未等落盘 | WAL + fsync + 多数派确认，三者缺一不可 |
| 数据凭空变旧（回滚） | 旧 Leader 复活写入 | Raft `term` + Fencing Token；存储层拒绝小于当前 epoch 的写 |
| 重试导致重复数据 | 超时后重试，实际两次都成功 | 幂等 requestId 去重；或用 CAS/版本号写入 |

**Merkle Tree 用于副本一致性校验**（Cassandra 的 anti-entropy repair）：把数据范围哈希成树，两副本自顶向下比对，只需传输哈希即可定位差异区间，避免全量数据比对。

## 7. 性能、扩展性与高可用

### 7.1 容量与性能规划

| 维度 | 估算方法 | 示例（10PB 对象存储） |
|------|----------|----------------------|
| 裸容量 | 逻辑容量 × 冗余系数 ÷ 磁盘利用率上限(0.8) | 10PB × 1.5(EC) ÷ 0.8 ≈ 19PB |
| 节点数 | 裸容量 ÷ 单机容量 | 19PB ÷ 每机 120TB ≈ 160 台 |
| 元数据量 | 对象数 × 单条元数据大小 | 100 亿 × 200B = 2TB（**必须分布式，不能单机内存**） |
| 网络 | 峰值吞吐 × 副本数（写放大） | 写 10GB/s × 3 = 30GB/s 内网需求 |
| IOPS | 峰值 QPS ÷ 单盘 IOPS × 放大系数 | 需按 LSM 写放大 10~30× 计算 |

### 7.2 高可用等级递进

```
Level 1  单机多盘       ── 容忍磁盘故障（RAID / 多副本落不同盘）
Level 2  多机同机架     ── 容忍单机故障
Level 3  多机架         ── 容忍机架/交换机/电源故障 ★ 生产最低标准
Level 4  同城多机房      ── 容忍机房级故障（延迟 1~3ms，可同步复制）
Level 5  跨地域多活      ── 容忍城市级灾难（延迟 30ms+，通常异步复制）
```

**关键权衡**：跨地域同步复制会让每次写入付上几十毫秒的 RTT，绝大多数业务不可接受。因此标准做法是：**同城三机房用同步（Raft 跨机房部署，5 副本），跨地域用异步复制**（接受 RPO > 0）。Google Spanner 用 TrueTime（GPS + 原子钟）实现全球强一致，代价是需要专用硬件基础设施——这也说明"全球强一致 + 低延迟"是需要硬件级投入才能突破的边界。

### 7.3 性能优化清单（按性价比排序）

| 优化项 | 收益 | 成本 |
|--------|:---:|:---:|
| WAL 组提交 | ⭐⭐⭐ 吞吐提升数十倍 | 低 |
| 批量写入（Batch）合并小请求 | ⭐⭐⭐ | 低 |
| 客户端路由缓存（免每次问元数据） | ⭐⭐⭐ | 低 |
| 数据压缩（LZ4/ZSTD） | ⭐⭐ 省 I/O 与空间 | 低（CPU 换 I/O） |
| 布隆过滤器减少无效磁盘读 | ⭐⭐ | 低 |
| 零拷贝 sendfile（大文件） | ⭐⭐ | 中 |
| ZGC 替代 G1 降低停顿 | ⭐⭐ P99 显著改善 | 低 |
| 读写分离 + 只读副本 | ⭐⭐ | 中 |

### 7.4 必须监控的核心指标

| 类别 | 指标 | 告警阈值参考 |
|------|------|--------------|
| **可靠性** | 副本数不足的分片数、损坏块数、巡检落后天数 | 副本不足 > 0 立即告警 |

| **均衡度** | 分片分布方差、热点分片 QPS 占比 | 单分片 > 集群均值 5 倍 |

## 8. 安全与合规

- **认证与鉴权**：对象存储用 AWS SigV4 签名机制（时间戳防重放 + HMAC 签名）；集群内部节点间用 mTLS 双向证书，防止恶意节点加入集群。
- **多租户隔离**：Bucket/Namespace 级隔离 + 配额（容量、QPS、带宽）+ **必须做租户级限流**，否则一个租户的突发流量会拖垮所有人（吵闹邻居问题）。
- **静态加密（At-Rest）**：SSE-S3 式服务端加密，两级密钥（每对象数据密钥 DEK + 主密钥 KEK，KEK 存 KMS/HSM）。**密钥绝不能与数据存在同一系统**。
- **传输加密（In-Transit）**：TLS 1.3；注意加密会削弱 sendfile 零拷贝优势，需权衡（可用 kTLS 缓解）。
- **删除语义**：软删除 + 回收站 + 版本控制（防误删与勒索病毒）；合规场景需**加密擦除**（销毁密钥即等效销毁数据，比物理擦除快得多）。
- **WORM 与合规留存**：金融、医疗场景需 Object Lock（一写多读，留存期内不可删改），满足审计要求。
- **数据主权与合规**：《数据安全法》《个人信息保护法》要求境内数据不出境、敏感数据分级；跨境复制需评估。
- **审计日志**：所有元数据操作（创建/删除/权限变更）必须留痕且日志本身不可篡改（追加写 + 独立存储）。

## 9. 总结与学习路径

### 9.1 核心结论回顾

分布式存储的本质，是**用软件在不可靠的硬件之上构建可靠的数据抽象**。其最大难点（第 2 节）不是任何单一算法，而是**在网络必然分区、节点必然故障的前提下，对"一致性、可用性、性能、成本"进行符合业务语义的取舍**——而且这个取舍必须显式做出、写进设计文档，因为存储是数据的最后防线，没有重来的机会。

三条最重要的实践原则：

1. **共识算法必须用成熟库**（Raft），自研主从切换是最经典的踩坑点。
2. **WAL + fsync + 多数派确认**是数据不丢的三件套，一个都不能省。
3. **能不自研就不自研**——95% 的团队应选云存储或 MinIO/Ceph/HBase，把精力留给业务。

### 9.3 面试高频考点速查

| 问题 | 回答要点 |
|------|----------|
| CAP 怎么选？ | P 必然发生 → CP/AP 二选一；更实用的是 PACELC；按数据分级而非全局统一 |
| Raft 如何避免脑裂？ | 任期 term + 多数派投票 + 一个 term 只能有一个 Leader + 日志匹配特性 |
| 为什么用 LSM 不用 B+Tree？ | 顺序写吞吐高、崩溃语义简单；代价是读放大与写放大 |
| 数据不丢怎么保证？ | WAL 先写 + fsync 落盘 + 多数派确认 + 端到端 CRC + 后台巡检 |
| 3 副本 vs 纠删码？ | 副本快省 CPU 但占 300%；EC 省空间但重建慢耗 CPU；热用副本冷用 EC |
| 扩容如何不影响业务？ | Learner 预热 + 分片表 Epoch + 迁移限流 + 可回滚 |
| 一致性哈希解决什么？ | 扩缩容只迁 1/N 数据；虚拟节点解决倾斜 |
| 写超时了数据到底写没写？ | 状态未知，必须靠幂等 requestId 安全重试 |
