## 1. 电商网站概述

### 1.1 什么是电商网站

电商网站是一类以**在线完成"商品展示 → 加购 → 下单 → 支付 → 履约 → 售后"完整交易闭环**为核心目标的系统。它的边界远大于"能下单的网页"——从 C2C 集市（淘宝）、B2C 自营（京东）、B2B 批发（1688），到跨境、垂直品类（生鲜/3C）、社交电商（拼多多）、SaaS 开店（有赞/Shopify），底层都共享一套核心领域：商品、库存、订单、购物车、促销、用户、支付、物流。

与普通内容型网站（`博客 / 论坛 / 资讯`）相比，电商系统的本质差异在于：**它是一个交易系统，而不是内容系统**。

| 维度 | 内容型网站 | 电商网站 |
|------|-----------|----------|
| 核心资产 | 文章 / 视频 / 帖子 | 钱、库存、订单 |
| 失败后果 | 看不到内容（体验差） | 丢单 / 超卖 / 错账（真金白银资损） |
| 一致性要求 | 弱（最终一致即可） | 强（库存、金额必须准确） |
| 流量特征 | 读多写少、峰值平缓 | 读多写多、**大促瞬时洪峰** |
| 最核心指标 | 访问量、停留时长 | GMV、转化率、资损率、可用性 |

### 1.2 一次下单背后的链路

```
用户点击「立即购买」
   │
   ▼
[网关/鉴权]  Token 校验、限流、防刷
   │
   ▼
[购物车/订单]  校验商品、收货地址、计算金额（含促销/优惠/运费）
   │
   ▼
[库存]  扣减可用库存（防超卖，原子操作）
   │
   ▼
[订单]  生成订单（状态机：待支付 → 已支付 → 已发货 → 完成）
   │
   ▼
[支付]  调用支付渠道（支付宝/微信），拿到支付凭证
   │
   ▼
[履约]  支付成功回调 → 扣减实物库存 → 通知仓储/物流 → 发货
   │
   ▼
[售后]  退款/退货/换货，反向冲正库存与账务
```

这条链路中，**任何一环的数据错误都是资损**：库存多扣则超卖赔付，少扣则超卖客诉；金额算错则要么亏本要么欺诈；订单丢失则直接丢 GMV。**交易数据的绝对正确，是电商系统不可逾越的底线。**

## 2. 设计电商网站面临的最大难点

很多人以为电商的难点是"页面多"或"对接支付"，那只是最浅的一层。**电商真正的难点，是在「极端瞬时流量」与「绝对交易正确」两个互相矛盾的要求下，把系统做稳、做对、做快。** 我们把它拆解为以下核心挑战，并标注最致命的一条。

### 2.1 ★ 最大难点：高并发交易场景下「一致性 × 高可用 × 高性能」的三角矛盾（不超卖、不丢单、不错账）

这是电商系统的"不可能三角"，也是一切架构决策的源头：

- **一致性（Correctness）**：库存不能超卖、订单不能丢、钱货必须对账一致。这是交易系统的生命线。
- **高可用（Availability）**：大促期间系统不能挂，挂 1 分钟就是数百万 GMV 损失 + 热搜舆情。
- **高性能（Performance）**：秒杀瞬时 QPS 可达日常数十倍甚至百倍，单请求必须毫秒级响应。

三者的张力体现在：

- 想保证**一致** → 要加锁、要事务、要强校验 → **吞吐下降、延迟上升**，大促直接被打挂。
- 想保证**高性能高可用** → 要异步、要缓存、要放开锁 → **稍有不慎就超卖、丢单、错账**。

工程上必须分层化解（见第 3、6 节）：用**缓存 + 原子扣减挡住并发洪峰**，用**数据库兜底保证最终正确**，用**异步化 + 消息队列削峰填谷**，用**分布式事务/最终一致保证跨服务数据对齐**。如何在这三角里为不同业务（普通下单 / 秒杀 / 预售）调好平衡点，是电商架构设计的核心命题。

> 一句话：**内容系统追求"尽量快"，交易系统追求"快且绝对不能错"——后者难一个数量级。**

### 2.2 复杂且多变的业务领域模型

电商是业务复杂度最高的系统之一，且需求持续演化：

- **核心域**：商品（SPU/SKU、类目、属性、品牌）、库存（可用/锁定/在途）、订单（正向+逆向）、购物车、用户/会员、促销（满减/折扣/优惠券/拼团/秒杀）、支付、物流、售后。
- **组合爆炸**：一个 SKU 可能同时命中"店铺满减 + 平台券 + 会员折扣 + 限时秒杀"，优惠叠加顺序与优先级直接决定金额正确性。
- **状态机极多**：订单有十几种状态与合法迁移；退款有"仅退款 / 退货退款 / 换货"不同链路；任一步错乱都会资损或客诉。

### 2.3 流量洪峰与系统稳定性（秒杀 / 大促）

- 流量极度脉冲：平常 1 万 QPS，大促开门红瞬时冲到 50 万 QPS，且集中在少数热点商品（爆款）。
- **缓存三连击**：缓存穿透（查不存在的 SKU）、缓存击穿（热点 Key 失效瞬间打库）、缓存雪崩（批量 Key 同时失效）。
- 数据库是最终瓶颈：无论怎么加缓存，扣库存、落订单终究要写 MySQL，单行热点（爆款库存）是性能天花板。

### 2.4 分布式事务与跨服务数据一致性

微服务拆分后，"下单"要跨订单、库存、用户、促销、支付多个服务：

- 订单库、库存库往往分库，无法用单机数据库事务。
- 典型难题：**库存扣了但订单没生成（少卖）、订单生成了但库存没扣（超卖）、支付成功但履约没触发（丢单）**。
- 强一致（2PC/XA）阻塞严重、基本不用；业界主流走**最终一致**（事务消息 / Seata / 本地消息表），但要把"补偿、重试、对账"做扎实。

### 2.5 数据一致性与异构存储同步

- 商品数据同时存在于 **MySQL（源）、Redis（详情缓存）、Elasticsearch（检索）**，任一处落后都会导致"搜得到买不到 / 价格不一致"。
- 库存扣减要同步更新缓存与数据库，双写顺序与失败处理容易出 bug。
- 近实时一致性（上架 1 秒内可搜到）与写吞吐需要权衡。

### 2.6 安全与风控（资损高发区）

- **防超卖**本质是并发安全，也是风控。
- **支付安全**：回调伪造、金额被篡改（前端传的金额不可信）、重复支付、重复发货。
- **黑产薅羊毛**：脚本抢券、虚假交易刷单、黄牛占库存。
- **合规**：个人信息保护、支付资质、等保要求。

## 3. 整体设计思路与实现路径

### 3.1 核心思想：领域驱动 + 分层解耦 + 异步削峰

电商架构的基石是三句话：

1. **按领域拆分（DDD）**：把庞大业务切成商品、订单、库存、用户、促销、支付等独立域（微服务），各自演进、独立扩容。
2. **读写分离 + 缓存前置**：读多写少，详情页/列表页走缓存与 CDN；写（交易）链路极简、可控。
3. **写操作异步化**：非核心步骤（发券、积分、通知、物流推单）扔进消息队列，主链路只做"扣库存 + 落订单 + 调支付"三件生死攸关的事。

### 3.2 总体架构（分层 + 微服务）

```
                         ┌──────────────────────────────────┐
                         │           用户 / APP / H5 / PC      │
                         └───────────────────┬──────────────┘
                                             │  HTTPS
                         ┌───────────────────▼──────────────┐
                         │  接入层：CDN + 网关(Gateway)        │
                         │  限流 / 鉴权 / 路由 / 防刷 / WAF     │
                         └───────────────────┬──────────────┘
                                             │
        ┌────────────────────────────────────▼────────────────────────────────┐
        │                     业务微服务层（Spring Cloud Alibaba）              │
        │ ┌────────┐ ┌────────┐ ┌────────┐ ┌────────┐ ┌────────┐ ┌────────┐   │
        │ │ 用户   │ │ 商品   │ │ 购物车 │ │ 订单   │ │ 库存   │ │ 促销   │   │
        │ └────────┘ └────────┘ └────────┘ └────────┘ └────────┘ └────────┘   │
        │ ┌────────┐ ┌────────┐ ┌────────┐ ┌────────┐ ┌────────┐              │
        │ │ 支付   │ │ 物流   │ │ 搜索   │ │ 会员   │ │ 风控   │              │
        │ └────────┘ └────────┘ └────────┘ └────────┘ └────────┘              │
        └───────────────────────────────┬────────────────────────────────────┘
                                         │  RPC(OpenFeign/Dubbo) + MQ
                         ┌───────────────▼────────────────┐
                         │   中间件层                       │
                         │  Redis(缓存/分布式锁)  MQ(削峰)  │
                         │  ES(检索)  Seata(分布式事务)     │
                         │  Nacos(注册配置) Sentinel(限流)   │
                         └───────────────┬────────────────┘
                                         │

                         │   存储层                         │

                         │  Redis 集群   ES 集群             │
                         └─────────────────────────────────┘
```

### 3.3 关键设计决策

| 决策点 | 做法 | 解决的难点 |
|--------|------|-----------|
| 库存扣减 | Redis 原子预扣 + 数据库 `WHERE stock>=count` 兜底 | 2.1 超卖、2.3 热点 |
| 下单主链路 | 只做"锁库存→落单→调支付"，其余异步 | 2.1 高性能、2.3 削峰 |
| 跨服务一致 | RocketMQ 事务消息 / Seata 最终一致 + 对账 | 2.4 分布式事务 |
| 热点商品 | 本地缓存(Caffeine) + Redis + 单号分段 | 2.3 击穿、3.2 缓存 |
| 检索 | ES 独立索引，CDC 同步商品 | 2.5 异构同步 |
| 稳定性 | 限流 + 熔断 + 降级 + 多级缓存 | 2.3 洪峰 |

### 3.4 商品与库存的领域建模要点

- **SPU / SKU 分离**：SPU（Standard Product Unit）是"iPhone 15"这个商品；SKU（Stock Keeping Unit）是"iPhone 15 128G 黑色"这个可售卖最小单元。库存、价格挂在 SKU 上。
- **库存三态**：可用库存（可卖）、锁定库存（已下单未支付，支付超时释放）、在途库存（采购未入库）。扣减顺序：可用 → 锁定；支付成功 → 锁定转实物扣减；取消/超时 → 锁定回可用。
- **价格与优惠分离**：商品标价、会员价、促销价、优惠券分别建模，下单时统一"计价引擎"计算，避免散落各处的 if-else 导致金额错误。

### 3.5 实现路径（里程碑）

| 阶段 | 目标 | 关键产出 |
|------|------|----------|
| M1 单体商城 | 跑通"商品→加购→下单→支付"最小闭环 | Spring Boot + MyBatis + MySQL 单体 |
| M2 缓存与异步 | 商品缓存、下单异步通知 | Redis + MQ 接入 |
| M3 微服务拆分 | 订单/库存/商品独立部署 | Spring Cloud Alibaba 集群 |
| M4 高并发专项 | 库存防超卖、秒杀、限流 | Redis+Lua、Sentinel、分布式事务 |
| M5 搜索与营销 | 商品检索、优惠券、推荐 | ES + 促销中心 |
| M6 工程化 | 支付对接、监控、压测、降级 | 生产可用、可观测 |

## 5. Java 技术栈的具体实现方式与核心技术

Java 是电商后端的主场语言（阿里/京东/美团核心交易均为 Java）。落地分两条主路线。

### 5.1 路线 A：基于 Spring Boot + Spring Cloud Alibaba 的微服务电商（最务实，推荐）

**技术栈全景**：

```
接入：Spring Cloud Gateway（网关/限流/路由）
注册配置：Nacos
熔断限流：Sentinel
RPC：OpenFeign（或 Dubbo）
分布式事务：Seata
缓存：Spring Data Redis（Redisson 分布式锁）
MQ：Spring Cloud Stream + RocketMQ
存储：MyBatis-Plus + MySQL（ShardingSphere 分库分表）
检索：Spring Data Elasticsearch
安全：Spring Security + JWT / Sa-Token
对象存储：阿里云 OSS SDK / MinIO
支付：支付宝 / 微信支付官方 SDK
```

**Spring Boot 下单服务骨架示例**：

```java
@RestController
@RequestMapping("/api/order")
@RequiredArgsConstructor
public class OrderController {
    private final OrderService orderService;
    private final IdempotentService idempotentService;

    @PostMapping
    public Result<Long> create(@RequestBody @Valid CreateOrderReq req,
                               @RequestAttribute("userId") Long userId) {
        // 1) 幂等校验：防止前端重复提交（见 5.4）
        idempotentService.checkAndMark(req.getToken(), userId);
        // 2) 主链路：锁库存 → 落订单 → 发起支付
        Long orderId = orderService.createOrder(userId, req);
        return Result.ok(orderId);
    }
}
```

**订单领域服务（含库存扣减调用）**：

```java
@Service
@RequiredArgsConstructor
public class OrderService {
    private final InventoryClient inventoryClient;   // OpenFeign 调库存服务
    private final OrderMapper orderMapper;
    private final RocketMQTemplate mq;

    @Transactional
    public Long createOrder(Long userId, CreateOrderReq req) {
        // 1) 调用库存服务原子扣减（内部 Redis+Lua + 数据库兜底）
        boolean ok = inventoryClient.deduct(req.getSkuId(), req.getCount());
        if (!ok) throw new BizException("库存不足");

        // 2) 落订单（状态：待支付）
        Order order = Order.create(userId, req);
        orderMapper.insert(order);

        // 3) 发送「待支付」延迟消息：30 分钟未支付则自动取消并释放库存
        mq.asyncSend("order:wait-pay", order.getId(),
                     msg -> msg.setDelayTimeLevel(5));  // RocketMQ 延迟级别
        return order.getId();
    }
}
```

### 5.4 幂等性与防重复提交（Java 示例）

交易系统必须对所有写接口做幂等，否则网络重试 / 用户连点会造成重复下单、重复扣款。

```java
// 基于「一次性 token」的幂等：下单前前端先取 token，提交时携带，服务端原子校验并删除
public void checkAndMark(String token, Long userId) {
    String key = "idempotent:order:" + userId;
    // Lua 保证「取值+删除」原子，并发下不会重复通过
    String lua = "if redis.call('get',KEYS[1])==ARGV[1] then "
               + "return redis.call('del',KEYS[1]) else return 0 end";
    Long r = redisTemplate.execute(
        new DefaultRedisScript<>(lua, Long.class),
        Collections.singletonList(key), token);
    if (r == null || r == 0) throw new BizException("重复提交或 token 已失效");
}
```

另一类幂等靠**数据库唯一约束 + 去重表**：支付流水号、订单号设唯一索引，重复写入直接抛 `DuplicateKeyException` 被捕获忽略。

## 6. 高并发交易链路专项：库存、秒杀与分布式事务

本节是化解第 2.1 节"不可能三角"的核心，也是电商 Java 实现的技术高地。

### 6.1 库存扣减的三层防线

```
第 1 层（挡洪峰）：Redis + Lua 原子预扣减
   - 99% 的并发在 Redis 层被拦截（库存不足直接返回，不落库）
   - Lua 保证「判断+扣减」原子，无超卖
第 2 层（兜底）：数据库 UPDATE ... WHERE sku_id=? AND stock>=count
   - 即使 Redis 与 DB 短暂不一致，数据库行锁 + 数量校验保证最终不超卖
第 3 层（对账）：定时任务 + 支付/取消事件回库
   - 锁定库存超时释放；每日对账纠正缓存与 DB 偏差
```

**Redis + Lua 预扣减（原子、无超卖）**：

```lua
-- KEYS[1]=库存key  ARGV[1]=扣减数量
local stock = tonumber(redis.call('GET', KEYS[1]))
if stock == nil then return -1 end              -- 未初始化
if stock < tonumber(ARGV[1]) then return 0 end  -- 库存不足
redis.call('DECRBY', KEYS[1], ARGV[1])
return 1                                        -- 扣减成功
```

```java
DefaultRedisScript<Long> script = new DefaultRedisScript<>(LUA, Long.class);
Long r = redisTemplate.execute(script,
        Collections.singletonList("stock:" + skuId), String.valueOf(count));
if (r == null || r == 0) throw new BizException("库存不足");
// 预扣成功 → 发 MQ 异步落库 + 创建订单（数据库再兜底一次）
```

**数据库乐观锁兜底（行级安全）**：

```java
@Update("UPDATE t_inventory SET stock = stock - #{count} " +
        "WHERE sku_id = #{skuId} AND stock >= #{count}")
int deduct(@Param("skuId") Long skuId, @Param("count") int count);
// 返回 0 行 = 库存不足，事务回滚；返回 1 行 = 扣减成功（行锁保证并发安全）
```

### 6.2 秒杀架构

秒杀是"不可能三角"的极端形态（瞬时百万 QPS 抢少量库存），要点：

1. **流量拦截前置**：网关层按用户/设备/IP 限流 + 验证码/答题削峰，拦截 90% 无效请求。
2. **静态资源 CDN 化**：秒杀页、商品图全走 CDN，不回源。
3. **Redis 原子抢库存**：如 6.1 的 Lua 脚本，单 Key 串行化扣减。
4. **MQ 异步落单**：抢到资格后发消息，订单服务消费创建订单，避免大事务阻塞。
5. **库存预热**：活动前把库存加载进 Redis；活动结束清空。
6. **削峰填谷**：用 MQ 把瞬时写请求拉平到订单服务可承受的速率。

### 6.3 分布式事务：最终一致优先

跨"订单→库存→支付"无法用单机事务，业界主流是**最终一致**：

| 方案 | 思路 | 适用 |
|------|------|------|
| **RocketMQ 事务消息** | 半消息→本地执行业务→Commit/Rollback；消费者保证至少处理一次 | 下单→扣库存→发券 |
| **Seata AT** | 代理 JDBC，自动生成 undo log，无业务侵入地回滚 | 同库多表/跨服务简单场景 |
| **本地消息表** | 业务表与消息表同库事务写入，定时任务投递 MQ | 无 Seata 时的朴素可靠方案 |
| **TCC** | Try(预留)/Confirm(确认)/Cancel(释放)，业务侵入强 | 强一致、资金类 |

**RocketMQ 事务消息（下单主链路）示意**：

```java
// 发送半事务消息，本地事务决定 Commit/Rollback
rocketMQTemplate.sendMessageInTransaction("order-tx",
    MessageBuilder.withPayload(orderDTO).build(),
    arg);  // arg 透传，在监听器里执行"落订单+扣库存"

// 监听器：本地事务执行
@RocketMQListerener(topic = "order-tx")
public class OrderTxListener implements RocketMQLocalTransactionListener {
    public RocketMQLocalTransactionState executeLocalTransaction(Message msg, Object arg) {
        try { orderService.createOrderAndDeduct((OrderDTO) arg); return COMMIT; }
        catch (Exception e) { return ROLLBACK; }
    }
    public RocketMQLocalTransactionState checkLocalTransaction(Message msg) {
        return orderService.exists(msg) ? COMMIT : UNKNOWN;  // 回查兜底
    }
}
```

> 关键纪律：**所有异步消费必须幂等**（靠订单号唯一索引 / 消费记录表），因为 MQ 至少一次投递，重复消费必然发生。

## 7. 性能、扩展性与高可用

- **多级缓存**：本地(Caffeine) → Redis → CDN，逐级拦截读流量；热点 Key 用「逻辑过期 + 互斥锁重建」防击穿。
- **读写分离与分库分表**：MySQL 一主多从扛读；订单/交易表按 `user_id` 或 `order_id` 哈希分片（ShardingSphere）。
- **异步化削峰**：下单非核心步骤（积分、通知、发票）全部 MQ 异步，主链路 RT 压到最低。
- **限流熔断降级**：网关 + Sentinel 做 QPS 限流、线程池隔离、熔断；极端流量下降级"商品评价/推荐"等非核心，保交易主链路。
- **库存单行热点**：爆款库存拆成多个子库存 Key（如 10 个子桶），分散单 Key 竞争；或 Redis 分段计数。
- **容量与压测**：大促前全链路压测（JMeter / 流量回放），按峰值 3 倍预留容量；预演扩容与降级预案。
- **可观测**：Prometheus 指标 + SkyWalking 链路追踪 + ELK 日志，秒级定位慢 SQL / 慢接口 / MQ 堆积。

## 8. 安全与合规

- **支付安全（最高优先级）**：
  - 金额永远由**服务端重新计算**，绝不信任前端传值。
  - 支付回调必须**验签**（支付宝公钥 / 微信平台证书），且做**幂等**（同一支付流水只处理一次）。
  - 支付状态以**异步回调 + 主动查单**双保险为准，不依赖前端跳转。
- **防超卖**：见第 6 节，Redis+Lua + 数据库兜底 + 对账三道防线。
- **防刷防薅**：设备指纹、行为风控、验证码/答题、频次限流、黑名单；优惠券领取绑定账号与库存。
- **越权防护**：订单/地址等接口必须校验"数据归属当前用户"（防水平越权），不能只靠登录态。
- **注入与 XSS**：用 MyBatis `#{}` 预编译、前端转义；禁止字符串拼接 SQL。
- **敏感数据**：手机号/地址加密存储，日志脱敏；传输全程 TLS。
- **合规**：遵循《个人信息保护法》、支付需对应资质；日志留存与审计满足等保要求。

## 9. 总结与学习路径

电商系统的本质，是**用工程手段在「一致性、高可用、高性能」三角里找平衡**。其最大难点（第 2.1 节）不是某个算法，而是如何在瞬时洪峰下持续做到"不超卖、不丢单、不错账"——这正是"缓存挡峰 + 数据库兜底 + 异步削峰 + 分布式事务最终一致"要联合解决的问题。

**给 Java 工程师的渐进式学习路径**：

1. **单体跑通**：Spring Boot + MyBatis-Plus + MySQL，手写"商品→加购→下单→支付（模拟）"闭环，吃透 SPU/SKU、订单状态机。
2. **加缓存与 MQ**：Redis 做商品详情缓存，RocketMQ 做下单异步通知，理解削峰。
3. **微服务拆分**：Spring Cloud Alibaba（Nacos/Gateway/Sentinel）把订单/库存/商品拆开。
4. **高并发专项**：Redis+Lua 库存扣减、数据库乐观锁兜底、Sentinel 限流、Seata/事务消息做分布式事务。
5. **搜索与营销**：Elasticsearch 商品检索、促销计价引擎、优惠券。
6. **支付与安全**：对接支付宝/微信支付（验签+幂等）、风控与防超卖三道防线。
7. **云原生**：Docker + Kubernetes 部署，Prometheus/SkyWalking 监控，全链路压测。

**一句话选型**：Java 团队做电商从 **Spring Cloud Alibaba 微服务**起步；高并发靠 **Redis+Lua + MQ + 分布式事务**；学习领域模型可用 **macrozheng/mall** 二开；无研发直接 **有赞/Shopify**。
