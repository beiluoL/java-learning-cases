# 代码评审清单

> 文档编号：ENG-CR-001  
> 版本：1.0  
> 生效日期：2026-10-26  
> 用途：**评审者逐项打勾；提交者自检；智能体在提交前必须自查一遍**  
> 强制力：**任何一项「❌ 阻断项」未通过，评审必须打回**  
> 上位文档：[`CODE_STANDARDS.md`](./CODE_STANDARDS.md) · [`QUALITY_GATE.md`](./QUALITY_GATE.md)

---

## 使用方式

1. 提交者先跑 `./scripts/verify.sh`，把结果贴进 PR 描述。
2. 提交者用第 1 节的「5 分钟自检」过一遍。
3. 评审者按第 2~11 节逐维度检查，**只对改动涉及的部分提问**，不做全量通读。
4. 发现「看起来有问题但不能确定」的，写进第 12 节，**不要猜**。

---

## 1. 五分钟自检（提交者必做）

> 这 5 条能拦掉本项目历史上 80% 的问题。

| # | 检查 | 命令 / 方法 | 通过标准 |
|---|---|---|---|
| 1 | 门禁全绿 | `./scripts/verify.sh` | 退出码 0，三域全 OK |
| 2 | 改了业务代码就启动调一次真实接口 | 起服务 + curl | 返回 `code=0`，字段符合预期 |
| 3 | 没有为「通过检查」而改测试 | 看 diff 里的测试文件 | 测试改动必须有独立理由 |
| 4 | 没有新增 `TODO` / 注释掉的代码 | `grep -rn "TODO\|FIXME"` | 0 处 |
| 5 | 文档与代码一致 | 对照改动的类/接口/表 | 相关 `.md` 已同步 |

## 2. 变更范围（最容易失守的一项）

| # | 检查项 | 结论 |
|---|---|---|
| 2.1 | 改动是否只做了一件事？混入了格式化/重命名/无关修复吗？ | ⬜ |
| 2.2 | 是否有「顺手」改的无关文件？ | ⬜ |
| 2.3 | 是否改变了业务行为？如果是，**有没有在 PR 里明确声明**？ | ⬜ |
| 2.4 | 是否升级了依赖或技术栈版本？（需单独评审） | ⬜ |
| 2.5 | 是否修改了已执行的 `V1~V5` 迁移文件？**（❌ 阻断）** | ⬜ |

> **「顺手改」是评审最大成本来源**：一个 30 行的 bugfix 里混进 300 行格式化，
> 评审者无法分辨哪行是真正的修复。
